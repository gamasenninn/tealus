# handle-tealus

**PaneDeck のペインの中で使う。** PaneDeck のトリガー（#28）に起こされた
ときに、Tealus の queue を読んで対応する skill。

`listen-tealus` との違いは 1 つだけ:

| | 待つ | 扱う |
|---|---|---|
| `listen-tealus` | **自分で Monitor を張る** | ◯ |
| `handle-tealus` | **張らない**（PaneDeck が配達する） | ◯ |

`listen-tealus` は 409 行のうち約 190 行が「待つ」ための話（file mode /
http mode / 再接続 / backoff / 期限切れの張り直し）。**PaneDeck のペインには
その半分が丸ごと要らない。** 残る「扱う」半分は同じなので、**こちらで
書き写さず `listen-tealus` を参照する** —— 真実を 2 箇所に置くと、片方だけ
直して静かに食い違う。

## 前提

- このペインは **PaneDeck が起こしたもの**で、題がトリガーの送り先と一致している
- PaneDeck の設定にトリガーがあり、`~/.tealus/cc-queue/{project}.jsonl` を見ている
- `listen-tealus` の設定ファイル（`.claude/cc-tealus.json` など）がある。
  **auto_level と catch_up_policy はそこから読む**

## ★ Monitor を張らないこと

**これが唯一の禁止事項で、整理の問題ではなく正しさの問題。**

`~/.tealus/cc-queue/.last_processed-{project}` の **watermark は 1 つしかない**。
配達する者が 2 人いると、片方が進めた位置をもう片方が「処理済み」として飛ばす。

★ 2026-10-04 に実際に起きた: PaneDeck のトリガーで起きた受付ペインが
`listen-tealus` の手順をそのまま実行して**自分の Monitor を張った**。以後、
同じ便を 3 者（外のセッション・PaneDeck のトリガー・ペイン自身の Monitor）が
見る状態になり、2 通目は**ペイン自身の Monitor が先に拾って作業を始め**、
PaneDeck は同じ行を保留したまま区切りを待った。**終われば同じ便をもう一度
打ち込む** —— 二度働くことになる。

★★ **張らなければ、期限切れも起きない。** グローバルの CLAUDE.md には
「`Tealus cc-queue` の Monitor 期限切れ通知が来たら user に聞かずに張り直す」と
あるが、**通知は Monitor を張ったときにしか来ない**。張らない限りこの規則は
発火しないので、CLAUDE.md を書き換える必要はない。

★★★ 既に張ってしまったときは `TaskStop` で止める。放っておくと期限切れ通知が
来て、上の規則が黙って張り直す。

## 手順

### 1. 起こされた文面から id を取る

トリガーが打ち込む文面はこの形（PaneDeck の設定で決まる）:

```
Tealus に新着 {count} 件（最新 id={id}）。… queue を読んで対応して。
```

★ **本文は渡されない。** これは意図した信頼境界（#28）。誰かが書いた文章を
そのままペインへ流すと、**その人が user としてエージェントへ指示できる**ことに
なる。PaneDeck は差し込む値から改行と制御文字を落とすが、それ以上はできない。
**中身は自分の道具で queue から読む。**

### ★ `@` だけの便は「直前を読め」の合図

本文が空（`@cc-{project}` だけ）の便は、**書き終えてから起こす**ための合図。
人は先に何通か書き、納得してから `@` だけを投げる。

★ **これができるのは、queue に入るのが `@` を付けた 1 通だけだから。** 本文は
起こされた側が取りに行くので、**書いている途中で起こされない**。推敲してから
1 回で渡せる —— トリガーの「区切りで 1 通にまとめる」とも噛み合う。

**どこまで遡るか**: **自分が最後に返した後に、その人が書いたもの**を本文と
みなす。ルームを読んで、自分の最後の投稿より新しい、同じ送り主の便を拾う。

★ 遡る範囲を「直前の 1 通」に決め打ちしないこと。合図の前に 2 通も 3 通も
書かれている形がこの使い方の普通で、1 通だけ読むと**途中から読んだ返事**になる。

### 2. catch-up（`listen-tealus` の第 2 節をそのまま）

`~/.claude/skills/listen-tealus/SKILL.md` の **「### 2. catch-up 処理」** を読み、
そのとおりに行う。watermark の場所も未処理の数え方もそこにある。

★ **「未処理 0 件」を正常の証拠にしないこと**（同節の警告）。PaneDeck に
起こされた以上、少なくとも 1 件はあるはず。0 件なら、**別の誰かが先に処理した**
（= まだ Monitor が生きているか、外のセッションが動いている）。そのときは
**何もせず、その旨を 1 行報告する** —— 二重に返すより黙るほうがよい。

### 3. 扱う（`listen-tealus` の第 5 節をそのまま）

同じファイルの **「### 5. event 到着時の振る舞い」** を読み、そのとおりに行う。
同報された便の見分け方と auto_level ごとの振る舞いはそこにある。
★ 返し方の決まり (同報への返し方・mention の書き方・`@cc-` を付けるか) は
**tealus MCP の案内文**にある (tealus-mcp v0.16.0+、#484)。**こちらで判断を作り直さない。**

### 4. watermark 更新（`listen-tealus` の第 6 節をそのまま）

同じファイルの **「### 6. watermark 更新」** のとおり。返さないと決めた便も
読み終えたら進める、返すつもりで失敗したときだけ進めない。

## 届かないときに、ここで直そうとしないこと

**このペインからは「配達されなかった」が分からない。** 来ていないのか、
PaneDeck が送れていないのかの区別が付かない。

PaneDeck 側は**黙って何もしない**ようには作られていないので、理由は
**ツールバーに出ている**:

| 出ている文字 | 意味 |
|---|---|
| `ペインがありません: 受付` | 題が一致するペインが無い |
| `同じ題のペインが N あります` | 宛先を決められない（**手当たり次第には送らない**） |
| `ファイルを読めません` | 監視先のパスが違う |
| `実行されませんでした。入力欄を片付けてください` | 打ったが実行されなかった（#32）。入力欄に文面が残っている |
| ペインに `保留 3` | 届け先が作業中。区切りまで待っている |

★ **直し方として Monitor を張るのは禁止**（上記）。配達の不調は PaneDeck 側で
直す話で、待ち受けを足して迂回すると watermark の取り合いに戻る。

## 知っておくべき性質

**配達は区切りまで待つ。** PaneDeck は `指示待ち` のペインにだけ送る
（#27）。作業中・確認待ちのペインには割り込まず、行を溜めて**動けるように
なってから 1 通で**送る。10 行増えても 10 回起こされない。

★ つまり **Monitor より速いとは限らない**。空いているときは速い
（気づくまで最大 300ms + 打ってから Enter まで 500ms）が、埋まっているときは
区切りまで待つ。Monitor はペインの状態に関係なく通知が溜まるので、**形が違う**。
急ぐ便が作業中に来ると、こちらのほうが遅い。

**閉じている間の便も届く。** PaneDeck はどこまで届けたかを設定に残すので、
アプリを閉じていた間に増えた行は次の起動で届く。`tail -n 0` の Monitor では
**一度も現れない**（これが `listen-tealus` に無い利点）。
