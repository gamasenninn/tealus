## 1. 何を作るのか

### 1.1 今のやり方と、その不便

利用者は AI に「残りのタスク・自分のやること」を会話から拾って一覧にしてもらい、HTML を部屋のファイルとして保存し、
印刷して 1 件ずつ片づけている (2026-11 から。取りこぼしが減った、という評価)。

不便は 2 つ:

| 不便 | 原因 |
|---|---|
| 毎回 (毎時) 作り直して保存・印刷する手間 | 一覧が「保存した 1 枚」で、更新されない |
| 残っているものを一望できない | 1 枚ごとに別のファイル。済んだか残っているかは、人が紙で覚えている |

### 1.2 TODO タグを使わない理由

一覧の 1 件は**会話のあちこちから AI がまとめたもの**で、投稿 1 件とは対応しない
(例: 「dbbackup の移行を始めてよいか」は、何本もの投稿と班のやりとりから生まれた 1 件)。
TODO タグに寄せると「どの投稿に付けるか」を毎回決めることになり、まとめた 1 件が置けない。

### 1.3 作るもの (一言で)

**「タスク」を 1 つ足す。** 1 件ずつ持ち、AI が足す・まとめる、人が済みにする。画面は一覧 1 枚 (スマホでチェック・そのまま印刷)。

## 2. 原則

1. **一覧は「人」のもの。部屋は「どこから来たか・何の話か」の括り** (利用者: 「部屋ごとでくくれば、そのタスクがなんの意味かもわかる」)
2. **済みにするのは人。** AI は「済んだようです」の印を付けるところまで (§4.3)
3. **元の会話へ戻れる。** 1 件は元の投稿へのリンクを持てる。開けるかどうかは今までどおり部屋の権限で決まる
4. **一人から始めて、社員へ広げる。** 最初は利用者 1 人で使い、作りは最初から「人ごとの一覧」にしておく (§7)
5. **本体の中に置く。** 別アプリ + MCP にしない (§9)

## 3. データ

`tasks` 表を 1 つ足す。

| 列 | 型 | 意味 |
|---|---|---|
| id | UUID | |
| owner_id | UUID → users | **誰の**タスクか |
| room_id | UUID → rooms, NULL 可 | 括りの部屋。NULL は「部屋なし」(個人のこと) |
| title | TEXT NOT NULL | 1 行 (印刷で 1 行に収まる長さを目安) |
| note | TEXT | ひとこと (なぜ・何を言えばよいか) |
| section | VARCHAR | `decide` 決める / `do` 手を動かす / `waiting` 待ち / `later` 今日でなくてよい / `held` **保留** (051、§8-7) |
| status | VARCHAR | `open` / `done` (051 で `held` を外した。保留は区分へ §8-7) |
| held_at | TIMESTAMPTZ, NULL 可 | **保留にした時刻** (051)。区分を保留に入れたときに入り、出したら消える。画面に「保留 11/28〜」 |
| source_message_ids | UUID[] | 元の投稿 (0 件以上) |
| ai_suggests_done | BOOLEAN | AI が「済んだようです」と見ている (§4.3) |
| created_by | UUID → users | 足した口座 (AI の口座か本人) |
| done_at / done_by | | 済みにした時刻と人 |
| sort_order | INTEGER | 同じ括りの中の並び |
| due_date | DATE, NULL 可 | **期限 (日付だけ)** (050、§8-6)。NULL は期限なし。「今日」「切れた」は日本の日付で決める |
| number | INTEGER | **会社全体の通し番号** (049。048 で人ごとに足し、同日 049 で全体に改めた §8-5)。済みにしても・持ち主が変わっても・グループのタスクになっても変わらない。消した番号は使い回さない |
| created_at / updated_at | | |

★ room_id を付けるときは **owner がその部屋のメンバーであること**を書き込みの口で確かめる (他人の部屋の話を括りに使わない)。
★ 部屋を消したら room_id は NULL に落とす (タスクは消さない)。部屋の名前は消えるので「(消した部屋)」と出す。

## 4. 書き込みと読み取り

### 4.1 本人 (画面)

- 一覧: 自分のタスクだけ。既定は `open` (区分が保留のものも並ぶ。数には入れない §5)、括りは **部屋ごと → その中で区分ごと**
- チェックで `done`、戻すこともできる。題・ひとこと・区分・部屋の直し、手で足す・消す
- ★ **各行に「直す」** (11-27): 題・ひとこと・区分・期限をその場で変える。期限は空にもできる
- ★ **お客様 (guest) は使えない** (11-27): 本人の口も AI の口 (頼んだ人がお客様) も 403。段階 1 は社員本人の一覧だけ (§7)。画面はお客様に「タスク」を出していないが、口が開いていた (ブラウザの試験で見つけた)
- 印刷: **いま画面で絞っているものをそのまま**印刷する (部屋・状態・区分で絞れば、必要な分だけ出せる。利用者の案 11-26)。見た目は今の HTML と同じ形 (Ctrl+P / iPhone は共有 → プリント)

### 4.2 AI (MCP の道具)

道具は 3 つ: `list_tasks` / `add_task` / `update_task`。

- **誰の一覧に書くかは「頼んだ人」で決める。** AI の道具は bot の資格で本体を呼ぶので、
  #564 の印 (`X-Tealus-Requester`) がある口だけで受け、owner = 頼んだ人に固定する。**印が無ければ断る**
  (cc ブリッジ・定時の仕事から書くときも、誰のためかを印で渡す)
- 足すときに元の投稿を付ける。付けられる投稿は、頼んだ人が入っている部屋のものだけ
- まとめ直し: 同じ話の 2 件を 1 件にするときは、片方を `update` で直し、もう片方は `ai_suggests_done: true` + ひとこと「○○にまとめた」(本人が押して済みにする)
- ★ **期限を入れてよいのは 2 つだけ** (11-27 利用者): (1) 会話にはっきり日が出ているとき (「金曜まで」「30 日に」) に日付へ直して入れる。(2) **AI が自分で決めた日** (「12-04 に数え直す」のような観測データの振り返り) — このときはひとことに「AI が決めた日」と書く。どちらでもなければ空のまま。**見当で付けない**
- ★ **AI は保留に入れない・出さない** (11-28): 保留は「やるかどうかを止める」人の判断。区分を `held` にする・`held` から変えるのは本人の口だけ (AI の口は 400)。足すときも `held` は受けない
- ★ 作ったときに決めたこと (2026-11-26): AI の口は **機械の口座 (is_bot) だけ**・**印が無ければ 400** (印は自己申告なので、人の口座が付けると他人の一覧に書けてしまう)。**status は変えられない (400)・消せない**。足すときは status / ai_suggests_done を受け取らない (open から)

### 4.3 AI は済みにしない

AI が会話から「済んだ」と読んでも `ai_suggests_done = true` を付けるだけ。画面ではその件に印が出て、本人が 1 回押せば済む。
★ 理由: 一覧の価値は「取りこぼしが無い」こと。AI の読み違いで 1 件が黙って消えるのがいちばん悪い (壊れた値は沈黙より悪い)。
★ 本人が会話で「済んだ」と言ったときも同じ扱い (印まで)。押す手間は 1 回で、それより読み違いの方が高くつく。

## 5. 画面

- 入口: 上のメニューに「タスク」(数字バッジ = open の件数)
- 1 枚の一覧。部屋の見出し → 区分 (決める / 手を動かす / 待ち / 今日でなくてよい) → 1 件 1 行 (チェック・題・ひとこと・元の会話へ)
- 「済んだようです」は行の横に小さく。押すと済み
- 絞り: 部屋 / 状態 (残り・済み・保留)
- 印刷用の見た目: 色を落とし、チェック欄を□にする
- ★ **期限** (11-27): 題の後ろに「〆11/30」。期限切れ (今日より前・まだ済んでいない) は赤で「期限切れ」、今日までなら橙で「今日まで」。上のメニューのタスクの数字の横に、期限切れがあれば赤い数字も出す。印刷は色が落ちるので「期限切れ」「今日まで」を字で出す
- 並びは今のまま (区分の中で sort_order)。期限で並べ替えない (並びが毎日変わると番号で探しにくい)
- ★ **保留** (11-28、§8-7): 区分の 5 つ目で、部屋の中のいちばん最後。題名だけ灰色 (取り消し線なし・印刷では薄くしない)、題の後ろに「保留 11/28〜」。見出しの残りの数には入れない (時間稼ぎが効くように)。隠さない (見なくなる置き場にしないため)。入れる・出すは「直す」の区分で
- ★ **説明をたたむ** (11-28 利用者の案): 何回も見ていると説明 (ひとこと) は知っているので、題名の一覧を多く見たい。見出しの切り替え 1 つで全部たたむ / 全部出す (端末ごとに覚える。最初は出した状態)。たたんでいる間は、説明か元の会話があるタスクの題の前に ▸ を出し、押すとその 1 件だけ開く (1 件ずつの開け閉めは覚えない)。期限・保留の印と「済んだようです」はたたんでも出す (押してもらうもの)。「元の会話」は説明の側に入る (題の行を詰めない)。印刷は画面のとおり (たためば題名だけの紙)

### 5.1 マルチトークの帯 (2026-11-27 利用者が決定)

PC のマルチトーク (`/multi`) では、「タスク」を押しても画面を移らず、**パネルの右に縦長の帯**を出し入れする。
会話のパネルを見ながら、横でタスクがいつも見えている形。

- 出し入れ: 左の一覧の「タスク」と、マルチトークのツールバーの「タスク」。もう一度押すと隠れる。開いているかと帯の幅は覚えておく (端末ごと)
- 中身は §5 の画面そのもの (区分・絞り・足す・済み・直す・読み直す・期限の印)。「戻る」と「印刷」だけ外す (印刷は 1 枚の画面から)
- ★ 帯の「元の会話 ›」は、その部屋を**マルチトークのパネルとして開く** (左の一覧で部屋を押したときと同じ口)。新しく開くときはその発言へ飛ぶ。もう開いていれば前に出して、そのパネルの中で発言へ移る (最小化していれば戻す。11-27 16:11 利用者の指摘で「前に出すだけ」から直した)
- 帯の左の境目をつまんで幅を変えられる (300〜640px)
- パネルの整列は帯を除いた幅で並べる。帯を出したときに帯の下へはみ出るパネルは、内側へ寄せる (幅が入らなければ縮める)。ほかのパネルは動かさない
- スマホ・1 部屋の画面は今のまま (マルチトークは幅 1024 以上の画面だけ)

帯にした理由 (パネルの 1 枚にする案と比べて):
- パネルの中身は部屋の画面を枠 (iframe) で埋め込んだ別のアプリ。タスクをパネルにすると、「元の会話」で隣のパネルを開くのに枠の中から外へ知らせる道が新しく要る。帯ならマルチトークの中にそのまま置け、一覧と同じ口を呼ぶだけ
- パネルにすると「タイル整列」で部屋と同じマスに入り、部屋の並びが崩れる
- パネルの記録は「部屋 1 つ」の形で、部屋でないパネルを混ぜると整列・重複の確かめに手直しが広がる
- 使ってみて「動かしたい」となったら、そのときパネルを考える

## 6. AI がまとめる時機

**今と同じ。** 頼まれたとき (「今日のタスクをまとめて」) と、班が決めた定時 (朝の確認など)。
★ 投稿のたびに自動で拾う常駐は作らない (§9)。まとめは今も人が頼んで回っていて、それで取りこぼしが減っている。
変わるのは**書く先**だけ: HTML を保存する代わりに `add_task` / `update_task` で一覧を直す。

## 7. 社員へ広げるとき (段階 2)

段階 1 (利用者 1 人) で作りを変えずに済むよう、最初から owner ごとにしてある。広げるときに決めることは:

- 他人のタスクを見られるのは誰か (本人だけ / 管理者も / 同じ部屋の人も)
- 他人にタスクを渡せるか (担当の割り振り)
- AI が誰のためにまとめるか (各自が頼む / 管理者がまとめて)

★ これらは段階 1 では作らない。段階 1 は「本人だけが見る・本人の頼みで AI が書く」だけ。

## 8. 決めたこと・未決

決めた (2026-11-26、UI のイメージを見て):
1. 区分は 4 つ (決める / 手を動かす / 待ち / 今日でなくてよい) で始める
2. ~~期限の欄は無しで始める~~ → **11-27 に足すと決めた** (§8-6)
3. **印刷は画面の絞りに従う** (残り全部も、部屋 1 つ・区分 1 つだけも出せる)。「今日」の印は作らない

5. **番号は会社全体の通し番号** (11-26 18:47 利用者が決定)。番号は「行為の ID」で、存在そのものに意味がある → 個人でもグループでも唯一。
   - 人ごとの番号 (048) をやめた理由: 共有すると 1 枚の画面に「3 番」が何人分も並ぶ。タスクを他の人に渡すと番号が変わる (ID が持ち主しだいで変わる)。一番大きい番号を消すと使い回す
   - 日付入り (261126-1) は採らなかった: 口で言うには長い・日付は created_at にある・日が変わったら 1 に戻す仕組みと「何時で日を切るか」が要る。代わりに**画面と印刷で番号の横に作った日を出す** (例「1250 · 11/26」)
   - 弱いところ: 番号が大きくなり、自分の一覧では飛び飛びになる (issue 番号と同じ)。切り替えた時点ではタスクは小野さん 15 件だけで、作った順の 1〜15 だったので番号は 1 つも変わらなかった

6. **期限** (11-27 12:43 利用者が決定): 日付だけ (時刻まで決まっている仕事は少なく、時刻を入れると「何時を過ぎたら切れか」の決まりも要る)・AI は §4.2 の 2 つのときだけ入れる・知らせるのはまず画面だけ (§5)・印刷に出す・各行に「直す」を一緒に作る

7. **保留は区分にする** (11-28 02:56 利用者が決定)。状態 (status) の `held` はあったが、画面から入れる口が無く 0 件だった。当面やらないと決めたもの (タスク 11・13) は置き場が無く「済み」にしていた → 済みと「やめた」が見分けられない
   - 状態でなく区分にした理由: 今の区分のうち「待ち」「今日でなくてよい」はもう種類でなく「今どう扱っているか」で、保留も並べて筋が通る。置き場所 (部屋の最後)・印刷の見出し・「直す」の操作がそのまま使える。状態と区分に 2 つ「保留」があると紛らわしいので 1 つにした
   - 区別: 今日でなくてよい = やると決まっている・急がない / 待ち = やると決まっている・相手の返事待ち / 保留 = やるかどうか自体を止めている
   - 弱いところ: 保留から出すとき元の区分に戻らない (「直す」で選び直す)
   - 「見なくなる置き場」にしない: 隠さない・いつからかを出す

## 9. 作らないもの

| 別アプリ + MCP | 元の投稿を開けるかは部屋の権限を持つ本体にしか決められない。ログイン・バックアップ・写し (docs/10) がもう 1 組増える | 本体の外の人 (社外) と共有する一覧が要るとき |
