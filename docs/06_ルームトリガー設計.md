# ルームトリガー設計 — 条件が満たされたら定型メッセージを投稿する

**状態**: 設計 (2026-08-22)。実装前。
**発端**: 「毎朝の議事録作成」「溜まった画像の変換」「ヤフオク巡回」など、定時・定型のタスクが増えてきた。

---

## 1. 何を作るのか — 増える機能は 1 つだけ

**「条件が満たされたら、決まったメッセージを、決まったルームに、決まった名義で投稿する」** —— これだけ。

その先は既存の経路にそのまま乗る。認可も、配送も、エージェントの起動も、記録も、いま動いているものが
そのまま使われる。**新しい実行系を作らない**のがこの設計の要である
(参照: [[project_single_server_simplicity]] 「1台・1プロセス・同一オリジン」)。

### なぜこの形なのか

この系ではメッセージが唯一の起動口になっている。4 経路 (socket / bot / voice / LINE) はすべて
投稿に収束し、エージェントは mention を見て動く。**したがって「メッセージを投稿する」を自動化すれば、
その先の全部が自動化される。**

副産物として重要なのは、**トリガーが人の目に見える場所に残る**こと。普通のスケジューラは
「いつ何が動いたか」がログの奥に隠れるが、これはルームに証拠が残り、止めるのも設定を切るだけで済む。

## 2. 現に人がやっていること (2026-08-22 実測)

### 2.1 朝礼 — 1 対 1、即座、取りこぼし不可

```
08-21 03:38  video  小野哲
08-21 03:38  text   小野哲     「@アシスタント /light この動画から議事録を作成して」
08-21 03:39  text   アシスタント 議事録
08-22 01:47  video  小野哲
08-22 01:47  text   小野哲     「@アシスタント /light この動画から議事録を作成して」  ← 一字一句同じ
```

**判断ではなく転記。** 毎朝、同じ 1 行を、同じタイミングで、一字一句同じに打っている。

### 2.2 出品写真・動画 — N 対 1、遅延許容、冪等

画像が LINE から束で届き (複数人・0〜4 秒間隔)、人が頃合いを見て 1 行打つ。
トリガーまでの間隔は **3 分 / 6 分 / 15 分 / 2 時間 29 分** とばらばら。1 回のトリガーが
複数人の束をまとめて拾っている。

**打っている命令が「直近画像を」= 未処理を全部やれ、なので冪等。**
早く撃ちすぎても残りは次回拾われ、何度撃っても未処理が無ければ何も起きない。
→ **「束が終わったか」を機械が判定する必要がない。** ここが設計を単純にする鍵。

なお人がやると遅い (2 時間 29 分放置された束がある)。自動化の利得は手間だけでなく**速さ**にもある。

## 2.5 ★ 検知は webhook を待たない —— DB を見る (2026-08-22 実測で確定)

**最初この設計は「`message.created` webhook を聞いて動画の到着を知る」つもりだった。動かない。**

`fireWebhooks('message.created', ...)` の呼び出し箇所を全部数えると 4 か所しかない。

```
socket/handlers/message.mts:129   socket (画面から打つ)
routes/bot.mts:153                Bot API
routes/media.mts:309              メディア **転送**
routes/voice.mts:130              音声
```

**今回の対象はどちらもこの 4 つに入っていない。**

```
朝礼の動画      routes/media.mts:52 (通常アップロード) → ★ fireWebhooks なし
出品写真の画像   services/lineMessageBridge.mts        → ★ fireWebhooks なし (意図的)
```

`media.mts` は**同一ファイル内で通常アップロード (52行) と転送 (228行) の挙動が違う**。
転送には webhook / push が付き、通常アップロードには付いていない。

**各経路にフックを仕込む案は採らない。** それはこのコードベースが既に 3 回繰り返している失敗
(リンクプレビュー / プッシュ通知 / 今回の AI 通知) の再生産になる → #383。

**→ 検知は `messages` テーブルを見る。経路に依存しないので、今後 10 番目の経路が増えても壊れない。**

## 3. 仕組みは 1 つ。判定が 3 種類

**共通のポーリングループ 1 本**。N 秒ごとに起きて、設定ごとに「撃つか」を判定する。

| 判定 | 撃つ条件 | 間隔の目安 | 用途 | 冪等性 |
|---|---|---|---|---|
| `immediate` | 前回以降に該当種別の投稿があり、まだ撃っていない元メッセージがある | 10 秒 | 朝礼 | 不要 (1:1) |
| `every` | 前回の発火以降に該当種別の投稿がある | 30 分 | 出品写真 | 前提 |
| `schedule` | 指定時刻を過ぎ、その日まだ撃っていない | 1 分 | ヤフオク巡回 | 不要 |

**`immediate` が最大 10 秒遅れる**が、いま人が打っているのは「動画と同じ秒〜数分後」なので実質ゼロ。
実装が 3 種類から 1 種類になり、経路非依存にもなる。

**本文の内容による条件は作らない。** 「本文が〜を含んだら」を許すと、条件・優先順位・順序・重複排除・
リトライが必要になり、ルールエンジンという別の部品群になる。**種別と時刻だけなら有限で数えられる。**

**本文の内容による条件は作らない。** 「本文が〜を含んだら」を許すと、条件・優先順位・順序・重複排除・
リトライが必要になり、ルールエンジンという別の部品群になる。**種別と時刻だけなら有限で数えられる。**

### 3.1 `every` を「N 分静かなら撃つ」にしない理由

| | N 分静かなら撃つ | N 分ごとに、あれば撃つ (採用) |
|---|---|---|
| 状態 | タイマーを張り直し続ける | 前回発火時刻だけ |
| 投稿が途切れないと | いつまでも撃たない (待ちぼうけ) | 必ず撃つ |
| 束の途中で撃つと | 起きないよう工夫が要る | 起きるが未処理は次回拾われる |
| 再起動の取りこぼし | 別途対策が要る | **自動的に片付く** (下記) |

**再起動時**: サーバが 3 時間止まっていても、復帰後の最初の判定で「その間に該当投稿があったか」を
見るだけなので、溜まった回数ぶん連射せず **1 回だけ撃つ**。多重起動対策が構造的に不要になる。

### 3.2 `schedule` だけが持つ判断 — 過ぎた時刻

`every` と違い、`schedule` は「8 時に止まっていて 8 時 20 分に復帰した」を自分で決める必要がある。

**決定: 撃たない。ただし「撃たなかった」をログに残す。**
3 時間遅れて巡回が走るより翌朝に回る方が予測しやすい。猶予窓は**まだ起きていない問題なので作らない**。
起きたら足す。

### 3.3 投稿は `POST /api/bot/push` の中身を再利用する

**新しい投稿経路を作らない。** `routes/bot.mts:113-160` が必要なものを全部持っている。

```
1. room_members 確認 (非メンバーなら 403)   ← 名義の妥当性検査がここにある
2. INSERT (sender_id = 認証ユーザー)        ← 名義がそのまま乗る
3. io.to(room).emit('message:new')          ← 画面のリアルタイム更新 + 未読の数え直し
4. fireWebhooks('message.created')          ← ★ エージェントが起動する
```

未読は**クライアントが `message:new` を合図にサーバへ数え直しに行く**作り
(`client/src/components/room-list/RoomList.tsx:65` → `fetchRooms()`) なので、
socket 配信さえ届けばバッジも自動的に正しくなる。

**プッシュ通知は付いていない。これは欠落ではなく仕様として扱う。**
自動投稿されるのは機械向けの定型文で、毎回全員のスマホを鳴らすと通知そのものが無視される
(同じ問題の前例が `lineMessageBridge.mts` に記録されている: 画像を 1 枚ずつ鳴らすと実用にならない)。
**後から「LINE 経由と同じ抜け漏れだ」と判断して足さないこと。**

実装としては HTTP を叩かず、`push` の中身 (メンバー確認 → INSERT → emit → webhook) を
共通関数に切り出してトリガーから直接呼ぶ。認証を通す必要がなくなる。

### 4.1 ルームは ID と名前を両方書く

**`room_id` が正、`room` は人が読むための併記。**
ルーム名は変更できるので、名前だけだと改名で黙って動かなくなる (= また「沈黙」)。
**起動時に `room_id` の実在を照合し、無ければ warn を出す。** 名前が現在の名前と食い違う場合も warn
(壊れてはいないが、設定が古い合図)。

### 4.2 `enabled` は消さずに止めるため

行を削ると「元は何だったか」が失われる。**止める操作と消す操作を分ける。**

## 5. 名義と権限

**そのルームで通用する権限ならどれでもよい。** ルームのメンバーができることの範囲を超えないので、
新しい穴は開かない。

**ただし 2 つ制約を置く。**

1. **自動投稿と分かる印を付ける。**
   いまの記録は「小野哲が 03:38 に打った」と残る。自動化後も同じ見え方だと、後から
   「本人が打ったのか、仕組みが撃ったのか」が誰にも分からない。**トラブル時にいちばん知りたいのがそこ。**
   名義は設定した人のままでよいので、**区別が付く印だけ必須**
   (参照: [[feedback_silent_skip_log_distinction]])。

2. **設定した人と名義は同じ人に限る。**
   別々にできると、他人の名義で無人実行を仕込める。現行の 2 件はどちらも同一人物で足りる。

## 6. 外せない条件 (実装時のチェックリスト)

- [ ] **`types` に `text` を許さない。** ← ループ防止の本体はこれ (下記 6.1)
- [ ] **発火しなかったことも記録に残す。** 「議事録が来ていない」が「動画が無かった」なのか
      「壊れて動いていない」なのかを区別できること。**この機能でいちばん忘れられやすい部分**
- [ ] **同じ元メッセージで二度撃たない** (`immediate`)。message id で重複排除。
      **状態は再起動をまたいで残ること** (ポーリング方式なので、メモリだけだと復帰後に撃ち直す)
- [ ] **条件は種別のみ。本文を見ない。** LINE から本文つきテキストが届く実例があり
      (08-22 06:42「エンジン始動、走行、旋回…」)、種別で絞らないと誤爆する
- [ ] **`room_id` 実在チェック**を起動時に行う
- [ ] **時刻はすべて JST** (`schedule` の `at`)。UTC と混ぜない
      (参照: [[feedback_report_timestamp_jst]])
- [ ] **設定ファイルが壊れていたときの挙動を決める。** 起動を止めるか、その行だけ無視するか。
      **無視するなら必ず warn を出す** (黙って減らすと「設定したのに動かない」が沈黙になる)
- [ ] **テストで時計を注入できる形にする。** TDD 必須 (CLAUDE.md) で、この機能は時刻依存

### 6.1 ★ ループ防止の実態 —— 送信者による除外は現在動いていない

当初「エージェントの投稿では発火しない」と書いたが、**前提が違っていた。**

```
agent-server/.env:51-60
  CC_SKIP_SENDER_IDS は #213 で導入したが、#215 (2026-05-02) で
  先頭マッチング方式 (/^@cc-(...)/m) が primary defense になったため削除済。現在 未設定
```

いまループを防いでいるのは**「メンションが行頭にあるか」だけ**。エージェントの返信は本文中で
`@cc-*` を引用するので行頭に来ず、自然に skip される。

**したがってトリガー側の防御は「送信者を除外する」ではなく「`types` に `text` を許さない」。**
エージェントの返信は `text` なので、条件が `video` / `image` である限りループしない。
設定ファイルの検証で弾ける = 実装も簡単。

**なお「人間以外を除外する」という実装にしてはいけない。** 出品写真の画像は直近 7 日 154 件すべてが
`LINE Bridge` からの投稿で、人間以外を除外すると**永久に発火しない**。

## 7. 受け入れられる穴 (名前を付けておく)

```
画像が来る → 撃つ → エージェントが処理に失敗する
→ 次の周期: 新しい画像は無い → 撃たない → 失敗分が残る
```

エージェント側が「未処理」として保持しているので、**次に新しい画像が来た時に一緒に拾われる。**
画像は毎日来るので実質は自己修復するが、その日の残り時間は放置される。

**受け入れる。** ただし条件 6 の「撃たなかった記録」があること。
エージェント側の未処理状態を Tealus が問い合わせる案は**採らない** —— 結合が増えて両方が壊れやすくなる。

### 7.1 調べた結果、問題ではなかったもの (次に同じ心配をしないために)

**文字起こしとの競走 —— 無い。**

動画投稿から自動の文字起こし完了までは実測 45 / 45 / 53 / 63 秒。人はこの間 (動画と同じ秒) に
トリガーを打っており、「エージェントが未完了の文字起こしを読んで失敗するのでは」と一度懸念した。

```
routes/bot.mts:807
  // 7. transcribe + format を同期実行 (Bot endpoint は MCP からの synchronous call を想定)
  const rawText = await transcribeMessage(...)
```

**エージェントは自分で文字起こしを起こせる。** cache (`status='done'`) があれば即返り、無ければ
その場で走らせて `await` で待つ。取りに行けば必ず手に入るので競走は成立しない。
待ち時間の設定項目は**不要**。

## 8. 段階

**骨組みは最初から 3 種類ぶん作る。有効にするのは 1 件ずつ。**
後から `schedule` を足すと、タイマーの持ち方と「撃った記録」の形を作り直すことになる。

```
第 1 段  朝礼 (immediate) だけ有効化 → 実機で数日見る
第 2 段  出品写真 (every) を足す
第 3 段  ヤフオク巡回 (schedule) を足す
```

## 10. 「自動投稿と分かる印」の置き方 (2026-08-22 決定)

### ★ 接頭辞は使えない —— mention の先頭判定に当たらなくなる

```
agent-server/src/webhook/ccQueue.mts:48
  const CC_MENTION_RE = /^@cc-([a-z0-9](?:[a-z0-9-]*[a-z0-9])?)/m;
  // 「メッセージ (or 行) の先頭 に @cc-{project} がある場合のみ match」
```

`[自動] @cc-tealus-app 直近画像を…` と書くと `^` に当たらず、**エージェントが起動しない**。
機能そのものが動かなくなる。

しかもこの先頭限定は偶然ではなく、**自己ループ防止の主要メカニズム**として意図的に置かれている
(同ファイルのコメント: AI reply は本文中の非先頭位置で `@cc-*` を引用するので自然に skip される)。
**触ってはいけない場所。**

### 決定: 本文の 2 行目に置く

```
@cc-tealus-app 直近画像を作業フォルダーに変換保存して
— 自動投稿 (room-triggers: 出品写真・動画)
```

- `/m` フラグなので**改行直後も「先頭」扱い**。1 行目を元のまま保てば mention 判定に一切影響しない
- **エージェントに渡る指示文を汚さない**。末尾に付けると印が指示の一部として読まれる余地が残る

### 弱点 (名前を付けておく)

**本文の印は偽装できる。** 人が同じ文字列を手で打てば自動投稿に見せかけられるし、
印を消して手打ちすることもできる。「後から区別する」目的には十分だが厳密ではない。

本来は**本文の印 (人が読む) + 記録側の属性 (集計・絞り込み用、偽装不可)** の二本立てにすべき。
ただし記録側は列を足す話になるので、**第 1 段は本文だけで始める**。
朝礼 1 件を数日動かすにはそれで足り、件数が増えてから必要な形が見えてくる。
