# 二重化設計 — 書き込むのは常に 1 台、もう 1 台は温かい写しを持って待つ

★ 2026-10-16 起草。**未決事項が 4 つ残っている (§10)。** 決まるまでは §6 の「先にやること」だけを進める。
★ 経緯 (9/11 の移設の相談 → 9/12「やらない」→ 10/3「まずは止まらないため」→ 10/16 fable 監査) は §11。
★ **「両方で書ける二重化」を提案する前に §9 を読むこと。** 作らないと決めた理由と、再開する条件が書いてある。

## 0. 原則

1. **書き込むのは常に 1 台。** 2 台が同時に書く形 (両系・振り分け) は作らない (§9)
2. **1 台・1 プロセス・同一オリジンを崩さない。** 待機系は「同じ本体をもう 1 か所に止めて置いておく」だけで、本体の作りは変えない
3. **待機系は opt-in。** 既定の Tealus (採用者の 1 台構成) は何も変わらない。待機系を持ちたい組織だけが設定と手順書で足す

## 1. 何を守るのか

### 1.1 止まった記録 (2026-10-16 時点の全件)

| 日時 | 長さ | 原因 | 待機系で防げるか |
|---|---|---|---|
| 2026-09-06 13:49〜14:09 | 20 分 | 停電 → ルーター再起動 (回線ごと) | 同じ建物の待機系では防げない。**別拠点なら防げる** |
| 2026-09-21 02:07〜02:18 | 12 分 | OS のクラッシュ + 更新の再起動。**OS 復帰から本体起動まで 9 分は人待ち** | 切り替えが人の手なら、人待ちは消えない。**自動起動なら 3 分程度** |
| 計画再起動 (配備) | 1 回 5〜20 秒 | 人の操作 | 防げない (防ぐなら §9 の振り分け) |

★ **機械の故障による停止は 0 件。** 止まった時間の大半は**人待ち**と**同じ建物の停電**。
→ 待機系より先に、自動起動と外からの見張りを整える (§6)。

### 1.2 ★ 本当の価値は「失うデータの量」

| | 失うデータ (RPO) | 止まる時間 (RTO) |
|---|---|---|
| いま (毎日 1 回のバックアップ) | **最悪 24 時間分** | 別機で起こし直すなら数時間 |
| この設計 | **数秒** (非同期の常時コピー) | 数十分 (人が切り替える) |

★ 「止まらない」より **「失わない」** の方が、記録 (§1.1) に合った売りになる。

## 2. 構成

```
              入口 (Cloudflare など)
               │              │
         外向きトンネル    外向きトンネル        ← 両方の機械から外へつなぐ
               │              │                   (拠点内の中継機やポート転送に頼らない)
     ┌─────────┴────┐    ┌────┴─────────┐
     │ 主系 (拠点 A)  │    │ 待機系 (拠点 B) │
     │ 本体・AI・通話  │    │ 本体は止めておく │
     │ PostgreSQL  ──┼────┼→ PostgreSQL     │  常時コピー (非同期)
     │ メディア    ──┼────┼→ メディア       │  数分ごとに足していく
     │ 設定・鍵    ──┼────┼→ 設定・鍵       │
     └──────┬───────┘    └───────┬──────┘
            └── 閉じたネットワーク ──┘           ← DB を外へ開かない (WireGuard / Tailscale など)
              互いに生きているかを見る (§5)
```

- **待機系は別の拠点に置く。** 同じ建物だと停電と回線断で一緒に止まる (§1.1 の 9/6)
- **入口の中継機に待機系を置かない。** 入口そのものが単一障害点なので、同じ電源・回線・入口になり冗長化にならない
- **データ (DB・メディア・鍵) は自分の拠点だけに置く。** クラウドに置いてよいのは入口とトンネルの中継だけ (データ主権、`00_what-is-tealus.md`)

## 3. 写すもの

| もの | 写し方 | 注意 |
|---|---|---|
| **DB** | PostgreSQL のストリーミング複製 (非同期)。待機側は読むだけの写し | メジャー版と**イメージの系統 (alpine / glibc) を揃える** (文字の並び順が変わり、昇格後に索引が壊れる)。replication slot を使うなら `max_slot_wal_keep_size` を必ず置く (待機が止まると主系のディスクが WAL で埋まる)。この DB の規模なら slot 無し + `wal_keep_size` で足りる見込み (1 日の WAL 量は要実測) |
| **メディア** | 数分ごとに**足すだけ**のコピー (消したものは写さない = 誤削除が伝わらない) | ★ 添付は保存先へ直接書かれる (`server/src/middleware/upload.mts`)。**できて数分未満のファイルは写さない** (書きかけを拾う)。初回の数十 GB は既存のバックアップから運ぶ |
| **設定・鍵** | 変わったときに写す | `server/.env` (JWT / VAPID を**同じ値**にすると、切り替えてもログインとプッシュの登録が保たれる)・`server/config/` のローカル設定・agent-server の設定とプロンプト・ワークスペース・取り込み元の ttl。★ **忘れやすいのはここ** |

★ 切り替えた直後は「投稿はあるが添付がまだ」(数分遅れ) が起きうる。許容する。

## 4. 切り替えと戻し

### 4.1 切り替え (手で行う)

1. 主系が本当に止まっていることを確かめる (2 台が主系にならないように)
2. 待機の DB を昇格する
3. 待機系で本体 (と、範囲に入れたもの §8) を起動する
4. 入口を待機系へ向け替える

★ **自動切り替えは入れない (§9)。** 誤って切り替わると、2 台が主系になる事故 (split-brain) の方が重い。

### 4.2 ★ 戻し (旧主系が戻ってきたとき)

★ **旧主系で本体を 1 回でも起動すると、旧 DB へ書き始める。** 本体だけでなく、本体へ投稿する周辺の部品 (localhost 向きのもの) も同じ。
→ **旧主系は、本体を起動する前に DB を待機として作り直す。** `pg_rewind` が使えるか (data checksums / `wal_log_hints`) は要確認。使えなければ丸ごと写し直す (DB が小さいので現実的)。

### 4.3 訓練

**試していない切り替えは切り替えではない。** 定休日に四半期 1 回、切り替えと戻しを通す。

## 5. 見張り

- **写しが止まっても静か** なのがいちばんの穴。いざというとき古い写ししか無い
- 見るもの: 複製の遅れ (`pg_stat_replication`)・メディアのコピーの最後の成功・待機系の死活
- ★ 見張り (`09_見張り設計.md`) は主系の本体の中にいるので、**主系が死ぬと見張りも一緒に黙る。** 主系 → 待機・待機 → 主系の**相互の目**にする
- 既存の口に乗せられるもの: コピーの記録 → `backup_log` 型 / 待機系の死活 → `heartbeat` 型。複製の遅れは新しい型が要る

## 6. 先にやること (この順番で)

1. **自動で立ち上がるようにする** (サービス化、#484)。9/21 の 12 分はこれだけで数分になる
2. **本体の外から生死を見る** 仕組みを 1 本置く (本体の中の見張りは自分の停止を知らせられない)
3. **別の機械でバックアップから丸ごと起こす練習** (DB だけでなくメディアと本体まで)。★ この手順が、そのまま待機系の初回の組み立て手順になる
4. 待機系を**同じ拠点の別の機械**で試す (手順を作るための練習台。冗長化にはならない)
5. 別拠点に待機系を置く (§7 の移設と兼ねる)

## 7. 移設への使い方

待機系は**移設の道具**になる。

1. 移設先に待機系を作り、常時コピーで追いつかせる
2. 1 回切り替える (= 移設が終わる)
3. 旧機はそのまま待機系になる

★ 「移設中も止めない」と「冗長化」が 1 回の作業で終わる。

## 8. 範囲 (待機系で戻るもの)

| 戻る | 主系と一緒に戻る (待機系では止まる) |
|---|---|
| チャット (閲覧・投稿)・メディア | AI (agent-server)・通話 (rtc-server)・無線の送り込み・通話履歴の取り込み (★ 未決 §10) |

★ 待機系の画面で**見るだけ**使える形はおまけとして足せる。ただし次が要る:
- 起動時に動く仕事 (ルームトリガー・見張り・取り込み・文字起こしのやり直し・掃除) を止める設定
- 書き込みの口 (REST・socket) を早めに断り、画面に「閲覧専用」を出す
- 部屋を開くだけで書く経路 (既読 `routes/read.mts`・プッシュの登録) を送らない
- 新着は配信されないので、定期的に取りに行く

## 9. 作らないもの

| 作らないもの | 理由 | 再開する条件 |
|---|---|---|
| **2 台で同時に動かす (どちらからでも読み書き、書き込みは主系)** | 本体の作りを変える改修になる: 書き込みの送り分け、添付の主系送り、配信 (`getIo()` 31 か所) の集約と台をまたぐ通知、DB に行を持たないイベント (入力中・通話・AI の「考え中」) の中継、文字起こしのやり直しの受け持ち、メモリー上の状態 (在席・閲覧中・通話中など) の共有。手当てしないと、待機側の利用者に AI の返事・プッシュ・通話が届かない。`03_アーキテクチャ設計.md` §「同じ本体を複数台で振り分けるときに要るもの」と同じもの | 計画再起動の数秒も止められない、という要件が出たとき |
| **両方が独立に書ける (両系・後勝ち)** | PostgreSQL の論理複製は食い違いで止まる (自動の後勝ちには拡張か自前の同期層が要る)。編集の版・タグなどの UNIQUE が衝突する。付随処理 (AI・プッシュ・トリガー・文字起こし) が両側で動く。回線断の間、両側の AI は相手の会話を知らずに答える | **2 拠点に使う人がいて、拠点の間の回線が切れても両側で書き続ける**ことが要件になったとき |
| **ブリッジ (LINE ブリッジ型) で 2 台を同期** | ID が別々になり、返信・既読・編集・削除を全部対応づけることになる。止まらないための仕組みには向かない | 拠点ごとに別の Tealus を動かし、一部の部屋だけ行き来させたいとき (別の用途) |
| **自動切り替え** | 誤った切り替えで 2 台が主系になる方が重い | 切り替えの訓練が定着し、人待ちが問題になったとき |
| **入口の中継機・クラウドに待機系を置く** | §2 | — |
