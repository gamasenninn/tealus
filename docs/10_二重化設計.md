★ 経緯 (9/11 の移設の相談 → 9/12「やらない」→ 10/3「まずは止まらないため」→ 10/16 fable 監査) は §11。

## 0. 原則

1. **書き込むのは常に 1 台。** 2 台が同時に書く形 (両系・振り分け) は作らない (§9)
2. **1 台・1 プロセス・同一オリジンを崩さない。** 待機系の本体は**読むだけ**で、書き込みは受け付けない。本体の作りは変えず、「読むだけの状態」を 1 つ足すだけ (§2.1)
3. **待機系は opt-in。** 既定の Tealus (採用者の 1 台構成) は何も変わらない。待機系を持ちたい組織だけが設定と手順書で足す

## 2. 構成

```
              入口 (Cloudflare など)
               │              │
         外向きトンネル    外向きトンネル        ← 両方の機械から外へつなぐ
               │              │                   (拠点内の中継機やポート転送に頼らない)
     ┌─────────┴────┐    ┌────┴──────────┐
     │ 主系 (拠点 A)  │    │ 待機系 (拠点 B)  │
     │ 本体・AI・通話  │    │ 本体 (読むだけ)   │  ← 別のアドレスで常に動く (§2.1)
     │ PostgreSQL  ──┼────┼→ PostgreSQL      │  常時コピー (非同期)
     │ メディア    ──┼────┼→ メディア        │  数分ごとに足していく
     │ 設定・鍵    ──┼────┼→ 設定・鍵        │
     └──────┬───────┘    └───────┬───────┘
            └─── WireGuard (直結) ───┘          ← 2 台の間の裏の通路。DB を外へ開かない (§2.2)
              互いに生きているかを見る (§5)
```

- **待機系は別の拠点に置く。** 同じ建物だと停電と回線断で一緒に止まる (§1.1 の 9/6)
- **入口の中継機に待機系を置かない。** 入口そのものが単一障害点なので、同じ電源・回線・入口になり冗長化にならない
- **データ (DB・メディア・鍵) は自分の拠点だけに置く。** クラウドに置いてよいのは入口とトンネルの中継だけ (データ主権、`00_what-is-tealus.md`)

### 2.1 ★ 待機系の本体 —— 読むだけで常に動かす

待機系の本体は止めずに、**写しの DB を読むだけの本体**として別のアドレスで動かしておく。

**得られるもの**
- **主系が止まっている間も、過去のやりとりを見られる** (障害中に「昨日の指示を確かめたい」に答えられる)
- **毎日、実物で確かめている状態になる**: 同じ版の本体が写しで起動できるか / 設定と鍵が写っているか / メディアが見えるか / コピーが遅れていないか。止めておく形だと、これらは切り替える日まで誰も知らない
- そのまま見張りの片側になる (§5)

★★ **確かめられないもの**: 昇格・書き込み・入口の向け替え・起動時の仕事・AI・プッシュ。読むだけで動いていることは**切り替えられることの証明にならない**。四半期の訓練 (§4.3) は残す。

**「読むだけ」の決め方 —— DB の状態で決める**
- 本体は起動時に `pg_is_in_recovery()` を見る。**写し (recovery 中) なら読むだけの本体**として、昇格済みなら普通の本体として起動する
- 設定ファイルで役割を書かないので、**切り替えのときに設定を書き換える手順が無い** (昇格 → 本体を再起動するだけ)
- 昇格は人の手なので、本体が勝手に書ける側へ変わることはない。★ 走っている途中で昇格しても、**再起動するまでは読むだけのまま** (安全側)
- ★ 旧主系の DB を待機として作り直してから本体を起動すれば、旧主系の本体も自動で読むだけになる (§4.2)

**本体に要る改修** (fable 監査で数えたもの。数日の規模)
1. 読むだけのときは、起動時の仕事 (ルームトリガー・見張り・organon の取り込み・文字起こしのやり直し・通知の宛先の掃除・`app.mts` の起動時の 7 本) を動かさない
2. 書き込みの口を**早めに断る** (REST の POST / PUT / DELETE、socket の送信・既読・通話)。画面に「閲覧専用」の帯を出し、入力欄を閉じる。★ 通話 (`call:start`) は DB より先にメモリーへ「通話中」を残すので、その前で断る
3. 部屋を開くだけで書く経路 (既読 `routes/read.mts`・プッシュの登録) を送らない
4. 新着は配信されない (配信は書いた本体からしか出ない) ので、数十秒ごとに新しい分を取りに行く (`catchUp`)
5. まだ写っていない添付 (数分遅れ) の見せ方
6. 写しの遅れと「読めるか」を返す口 (§5)。メディアの「DB にはあるのにファイルが無い」件数 (§3.1) もここに入れる

**運用**
- 別のアドレスなので、利用者は一度ログインし直す (PWA も別に入れる)。**誰に開放するかは未決 (§10)**
- 待機系の側では agent-server と外からの受け口 (LINE など) は動かさない。本体へ投稿する周辺の部品が待機系へ向いていても、**書き込みは断られる** (黙って書かれるより良い)
- hot standby では、長い読み取り (検索など) が複製の適用とぶつかって切られることがある (`max_standby_streaming_delay` 次第)

### 2.2 2 台の間の通路 —— WireGuard を直接つなぐ (調整役を置かない)

**役割**: 2 台の間の**裏の通路専用**。利用者の通り道ではない (利用者は入口のトンネルから入る)。

| 通るもの | 中身 |
|---|---|
| DB の常時コピー | 待機系の PostgreSQL が主系の 5432 へ (いちばん大事) |
| メディアのコピー | rclone (SFTP) などがこの上を通る (§3.1) |
| 設定と鍵の写し | §3 |
| 相互の見張り | 互いの死活と写しの遅れ (§5) |
| 切り替えの作業 | 管理者が別拠点の機械に入る |

**形**
- 2 台は**互いの公開鍵とアドレスを最初に 1 回置くだけ**でつながる。真ん中に調整役 (コーディネーター) を置かない
- ★ **両方の拠点で UDP のポートを 1 つずつ開ける。** どちらからでもつなぎ直せるので、**落ちて困る真ん中の部品が無い**。片方の拠点しか開けられないときは、開けられない側から `PersistentKeepalive` で張り続ける
  - ★ §2 の図の「ポート転送に頼らない」は**利用者の入口**の話。裏の通路は別で、WireGuard の UDP を 1 つだけ開ける (鍵を持たない相手には応答しないので、外から見て何も無いのと同じ)
- 管理者のノート PC も、同じように 1 台分の鍵を足すだけ
- DB は 127.0.0.1 待ち受け (2026-09-28 の決定) を崩さない。WireGuard のアドレスで待ち受けを足すか、通路の中だけへ取り次ぐ。★ 当初は「どちらでも `pg_hba` で、複製用の利用者が待機系の通路のアドレスから来たときだけ通す」と書いていたが、**Docker Desktop の上では成り立たない** (下)
- ★★ **`pg_hba` では送り元を絞れない** (2026-10-17 実測、#605)。Docker Desktop (Windows) のポート公開は送り元を bridge の gateway (`172.17.0.1`) に付け替えるので、**待機系から来ても、主系の機械の中から来ても、DB には同じアドレスに見える**。絞りは `pg_hba` より手前に置く:
  1. WireGuard: 通路を通れるのは待機系の鍵だけ (AllowedIPs は待機系の通路アドレス /32)
  2. 複製の口を通路のアドレスにだけ出す (Docker のポート公開を `<通路のアドレス>:<ポート>` に限る。LAN や外には出さない)
  3. Windows のファイアウォールで、複製のポートを**待機系の通路アドレス以外は拒否**にする。★ Docker Desktop の受け口には「全ポート・どこからでも許可」の規則が入っているので、**許可ではなく拒否の規則**が要る
  4. `pg_hba` は gateway のアドレス + 複製用の利用者 + パスワード。アドレスでの絞りは期待しない
  - ★ それでも**主系の機械の中で動くもの**は通路のアドレスへつなげる。そこはパスワードで守る
- ★★ **待機系の側も同じ** (切り替えたあとは待機系が主系になり、旧主系がそこから写しを取る)。2026-10-17 の実験 (待機系 = macOS + colima) では、colima の器は通路のアドレスに直接ポートを出せず、`0.0.0.0` に出すと**家の LAN にも出た**。DB からは送り元が器の gateway に見えるので、`pg_hba` にパスワードの無い行があれば **LAN の誰でも複製を引ける**状態になる。器を `127.0.0.1` にだけ出し、**送り元を通路の相手に限る中継**を通路のアドレスに立てて避けた
  - 複製の口を出すときは、**どの機械でも「LAN から届かないこと」を実際につないで確かめる** (出したつもりの場所と、実際に出た場所が違う)
  - 主系から写した待機系は、主系の `pg_hba` もそのまま持つ。主系に緩い行があると、昇格した待機系でも緩い
  - ★★ **中継を書くなら、つないだあとに待ち時間を外す。** 実験の中継は「つなぐまでの 10 秒」の制限が、つないだあとの読み書きにも効き続けていた。複製の接続は WAL が出ないあいだ無通信なので、**10 秒ごとに切れて張り直していた** (39 回)。それでも `pg_stat_replication` は引くたびに `streaming`・遅れ数 ms を返したので、**1 回引くだけの確かめ方では通ってしまった**。中継には keepalive を入れ、閉じた理由をログに書く
  - ★ 確かめるときは `state = 'streaming'` だけでなく、**接続の寿命** (`now() - backend_start`) か**張り直しの回数** (待機側のログの `started streaming`) を見る
- ★ 鍵は**期限を持たない** (WireGuard の鍵に期限は無い)。通路が切れたら写しの遅れ (§5) で気づく

**★ 主系の外向きのアドレスが変わる場合** (2026-10-17 の実験で判明。本社の回線は固定 IP ではない見込み)
- 待機系は主系のアドレスへつなぎに行く。主系のアドレスが変わると、**待機系は古いアドレスへ送り続け、通路が黙って切れる** (写しも止まる)。変わるのはルーターの再起動やプロバイダの再接続のとき
- 直し方は 3 つ:
  | 案 | 中身 | 弱いところ |
  |---|---|---|
  | **固定 IP にする** (本命) | プロバイダとの契約を固定 IP にする | 月額の費用 |
  | 名前で探しに行く | 主系のアドレスにダイナミック DNS の名前を付け、待機系が数分ごとに引き直す (WireGuard は名前を起動時にしか引かない) | 主系のアドレスが名前から引けるようになる (今は入口の後ろに隠れている)。引き直す仕組みを別に持つ |
  | 気づいたら手で直す | 待機系のつなぎ先を書き換える | 気づくのが遅れる。**実験の間だけ**の扱い |
- どれでも、切れたことには §5 の見張り (写しの遅れ・最後の handshake) で気づく。**どれにするかは未決 (§10)**

**選ばなかったもの** (2026-10-16 調べ)

| 道具 | 選ばなかった理由 |
|---|---|
| Tailscale | 無料のプランは**家庭での非商用に限る**。業務は有料 (1 利用者 月 8 ドル〜)。調整役が他社のクラウドにあり、調整役そのものは OSS ではない。**採用者全員に有料の契約を求める既定にはできない**。★ 機械の鍵に既定で期限がある (切れると複製が静かに止まる) |
| Headscale (OSS の調整役) を 1 つ | 2 台なら調整役は要らない。運用するもの (外から届く置き場と Headscale) が増える |
| Headscale を 3 つ並べて冗長に | **公式には 1 台で動かす前提**で、複数台は支えられていない構成。各機械は調整役のアドレスを 1 つしか持てない。3 重にする仕組みのために別の二重化が要る。★ そもそも調整役が落ちても張ってある通路は動き続けるので、守れるものが少ない |
| 調整役を主系や入口の中継機に置く | 主系に置くと拠点ごと止まったときに一緒に止まり、データを持つ機械に外から入る口が増える。入口の中継機は共有の機械で、外から入る口を増やしたくない |
| NetBird | 調整役まで OSS で揃うが、2 台には大きい |
| SSH のトンネル | 切れたときの張り直しを自前で持つことになる |

★ **調整役が効いてくるのは機械が多いとき** (社員の端末・複数拠点・場所が動く)。機械が増えたら、その時点で**クラウドの小さな VM に Headscale を 1 つ**置く形へ移れる (データは通らないので主権に触れない。機械の側の作りは WireGuard のまま)。

## 3. 写すもの

| もの | 写し方 | 注意 |
|---|---|---|
| **DB** | PostgreSQL のストリーミング複製 (非同期)。待機側は読むだけの写し | メジャー版と**イメージの系統 (alpine / glibc) を揃える** (文字の並び順が変わり、昇格後に索引が壊れる)。replication slot を使うなら `max_slot_wal_keep_size` を必ず置く (待機が止まると主系のディスクが WAL で埋まる)。この DB の規模なら slot 無し + `wal_keep_size` で足りる見込み (1 日の WAL 量は要実測) |
| **メディア** | 数分ごとに**足すだけ**のコピー (消したものは写さない = 誤削除が伝わらない)。詳しくは §3.1 | ★ 添付は保存先へ直接書かれる (`server/src/middleware/upload.mts`)。**できて数分未満のファイルは写さない** (書きかけを拾う)。初回の数十 GB は既存のバックアップから運ぶ |
| **設定・鍵** | 変わったときに写す | `server/.env` (JWT / VAPID を**同じ値**にすると、切り替えてもログインとプッシュの登録が保たれる)・`server/config/` のローカル設定・agent-server の設定とプロンプト・ワークスペース・取り込み元の ttl。★ **忘れやすいのはここ** |

★ 切り替えた直後は「投稿はあるが添付がまだ」(数分遅れ) が起きうる。許容する。

### 3.1 メディアの写し方

メディアには DB の複製のような仕組みが無いので、**ファイルのコピーを数分ごとに回す** (毎日のバックアップの robocopy と同じ考え方を、間隔を詰めて別拠点へ向けたもの)。

**約束**
- **一方向・足すだけ。** 主系 → 待機系だけ。主系で消したものは待機系で消さない (誤削除・壊れて消えたものが伝わらない)
- **新しい・変わったファイルだけ。** 全体は数十 GB でも、1 日に増えるのは平均 250MB 程度 (バックアップの実績、2026-10)。数分ごとの量はふだん数 MB
- **書きかけを写さない。** 添付は受け取りながら保存先へ直接書かれる (`server/src/middleware/upload.mts`、一時ファイルを経由しない)。**できて 2 分未満のファイルは次の回に回す**
- **2 台の間の通路 (§2.2) 越し。** 外へは開かない
- **最初の 1 回はインターネット越しに運ばない。** バックアップの写しから持っていくか、ディスクで運ぶ
- **範囲は `MEDIA_ROOT` の下の全部** (voices・videos・images・files・thumbnails・stamps・avatars・line-* など)。サムネイルは作り直せるが、分けると手順が増えるのでまとめて写す

**道具**

| 道具 | 向き | 合う場面 |
|---|---|---|
| **rclone** (`copy --min-age 2m`) を数分ごとに | インターネット越しに強い (SFTP など)。消さない・書きかけを除く・OS を問わない、が設定だけで書ける | **別拠点の待機系 (本命)** |
| robocopy を数分ごとに | Windows どうし、共有フォルダ (SMB) 越し。新しい道具が増えない。ただし SMB はインターネット越しに遅く、書きかけを除く設定が弱い | 同じ拠点の別の機械での練習 (§6 の 4) |
| Syncthing | ほぼ即時。ただし既定は両方向で、消したものも伝わる (「送るだけ / 受けるだけ」と「消したものを無視」の設定が要る) | 即時性が必要になったとき |

★ どれにするかは §6 の練習の段で決める。

★ 実測 (2026-10-17、#605、近い 2 拠点・WireGuard 越し・rclone `copy --min-age 2m` → 待機側の `rclone serve sftp`): 画像 985 件・1.45 GB を **58 秒 (約 25 MB/s・200 Mbps)**。照合 (`check --one-way --size-only`) で差 0。練習用のフォルダで「主系で消したものは待機側で消えない」「できて 2 分未満は送らない」「古いものは送る」「変わらないものは送り直さない」の 4 つを確かめた。
- この速さなら初回の 35 GB は 25 分ほど。**近い拠点どうしなら初回も回線で運べる**。遠い拠点・細い回線では、上の「最初の 1 回はバックアップから」を守る
- 待機側の受け口は、OS の sshd でなく**利用者の権限で動く `rclone serve sftp` を通路のアドレスにだけ**出した。管理者の権限が要らず、渡した置き場の外を見せない (sshd は鍵が通ると家のフォルダ全体が見える)。受け口の鍵は主系の 1 本だけ、host 鍵は固定して主系側で指紋を照合する
- ★ お客様のファイルを写すときは、**道具の既定のログ** (`--log-level INFO` は 1 件ごとにパスを書く) も「外に出さないもの」に数える

**確かめ方 —— 「DB にはあるのに、ファイルが無い」を数える**
- DB はほぼリアルタイムに写るので、待機系の DB は「どの投稿がどのファイルを持つか」を知っている。待機系で **DB が指しているのに手元に無いファイルの件数**を数えれば、コピーの遅れと取りこぼしが分かる
- 数分以内に 0 へ戻るなら正常。**増え続けるならコピーが止まっている**
- ★ ファイルのコピーは失敗しても静か。この件数を読むだけの本体が返す「写しの状態」(§2.1 の 6・§5) に入れて、見張りが引けるようにする

## 4. 切り替えと戻し

### 4.1 切り替え (手で行う)

1. 主系が本当に止まっていることを確かめる (2 台が主系にならないように)
2. 待機の DB を昇格する
3. 待機系の本体を**再起動する** (起動時に昇格済みを読み取り、普通の本体として動く §2.1)。範囲に入れたもの (§8) を起動する
4. 入口を待機系へ向け替える

★ **自動切り替えは入れない (§9)。** 誤って切り替わると、2 台が主系になる事故 (split-brain) の方が重い。

★ 実測 (2026-10-17、#605、練習用の DB 117 MB): 昇格 (`select pg_promote();`) は **33 ms**。timeline が 1 → 2 に進み、待機系が最後に適用した位置は主系が止まった位置とぴったり一致した。**切り替えの時間を決めるのは DB ではなく、人が気づいて手を動かすまでと本体の再起動** (§1.1 の 9/21 は 12 分のうち 9 分が人待ち)。
★ 昇格したら `postgresql.auto.conf` の `primary_conninfo` を消す。昇格しても前のつなぎ先が残り、その DB から写しを取ると古い行も付いていく (後の行が効くので動くが、切り替えのたびに積もる)。

### 4.2 ★ 戻し (旧主系が戻ってきたとき)

★ **旧主系の DB が主系のまま本体を 1 回でも起動すると、旧 DB へ書き始める。** 本体だけでなく、本体へ投稿する周辺の部品 (localhost 向きのもの) も同じ。
→ **旧主系は、本体を起動する前に DB を待機として作り直す。** 作り直せば、本体は起動時に読むだけになる (§2.1)。★ `pg_rewind` は**今の本番では使えない** (2026-10-17 実測: `data_checksums` = off・`wal_log_hints` = off。`wal_log_hints` を入れるには DB の再起動が要る)。**丸ごと写し直す** (DB は 152 MB なので数分)。

★ 実測 (2026-10-17、#605): 旧主系の古いデータには触らず、**新しい置き場**に `pg_basebackup -R -X stream` で写して待機として起動 → 6.9 秒で写し終え、起動から 0.06 秒で新しい主系から streaming を受け始めた (timeline 2 を追う)。
- ★ `pg_basebackup` は**コンテナの postgres ユーザで**走らせる (置き場の持ち主を先に postgres にしておく)。root で走らせると `-R` が書く `passfile` が `/root/.pgpass` を指し、パスワードありの本番では DB (postgres ユーザ) が読めず複製が始まらない
- 古い置き場は消さずに止めておく (戻しが失敗したときの手がかり)。消すのは新しい待機が追いついてから

### 4.3 訓練

**試していない切り替えは切り替えではない。** 定休日に四半期 1 回、切り替えと戻しを通す。読むだけの本体が毎日動いていても、これは省かない (§2.1)。

## 5. 見張り

- **写しが止まっても静か** なのがいちばんの穴。いざというとき古い写ししか無い
- 見るもの: 複製の遅れ (`pg_stat_replication` / 待機側の最後の適用時刻)・メディアのコピーの最後の成功・待機系の死活
  - ★ 実測 (2026-10-17、#605、近い 2 拠点): 写しの適用の遅れはふだん **4〜9 ms**。写しが 3 分止まっても、つなぎ直してから 2 秒以内に追いつく (100.9 KB)。通路が 5 分切れても、写しは自分でつなぎ直す
  - ★ **待機側の `pg_stat_wal_receiver.status` は、通路が切れてから「切れた」に変わるまで 46 秒かかる** (戻るほうは 3 秒)。速く気づきたいなら、通路の死活 (ping か WireGuard の最後の handshake) を別に見る
  - ★ 待機側の `now() - pg_last_xact_replay_timestamp()` は**遅れではなく「最後の書き込みからの古さ」**。書き込みの無い時間も入るので、遅れの見張りに使うと静かな夜に誤報が出る
- ★ 見張り (`09_見張り設計.md`) は主系の本体の中にいるので、**主系が死ぬと見張りも一緒に黙る。** 主系 → 待機・待機 → 主系の**相互の目**にする
- ★ 読むだけの本体 (§2.1) が「写しの遅れ」と「読めるか」を返す口を持てば、主系や外の見張りがそれを引くだけで待機系の状態が分かる
- 既存の口に乗せられるもの: コピーの記録 → `backup_log` 型 / 待機系の死活 → `heartbeat` 型。複製の遅れは新しい型が要る

## 6. 先にやること (この順番で)

1. **自動で立ち上がるようにする** (サービス化、#484)。9/21 の 12 分はこれだけで数分になる
2. **本体の外から生死を見る** 仕組みを 1 本置く (本体の中の見張りは自分の停止を知らせられない)
3. **別の機械でバックアップから丸ごと起こす練習** (DB だけでなくメディアと本体まで)。★ この手順が、そのまま待機系の初回の組み立て手順になる
4. 待機系を**同じ拠点の別の機械**で試す (手順を作るための練習台。冗長化にはならない)。読むだけの本体 (§2.1) もここで作る
5. 別拠点に待機系を置く (§7 の移設と兼ねる)

## 7. 移設への使い方

待機系は**移設の道具**になる。

1. 移設先に待機系を作り、常時コピーで追いつかせる。読むだけの本体で、移設先で正しく見えることを**移設の前から**確かめておける
2. 1 回切り替える (= 移設が終わる)
3. 旧機はそのまま待機系になる

★ 「移設中も止めない」と「冗長化」が 1 回の作業で終わる。

## 9. 作らないもの

| 作らないもの | 理由 | 再開する条件 |
|---|---|---|
| **2 台で同時に動かす (どちらからでも読み書き、書き込みは主系)** | 本体の作りを変える改修になる: 書き込みの送り分け、添付の主系送り、配信 (`getIo()` 31 か所) の集約と台をまたぐ通知、DB に行を持たないイベント (入力中・通話・AI の「考え中」) の中継、文字起こしのやり直しの受け持ち、メモリー上の状態 (在席・閲覧中・通話中など) の共有。手当てしないと、待機側の利用者に AI の返事・プッシュ・通話が届かない。`03_アーキテクチャ設計.md` §「同じ本体を複数台で振り分けるときに要るもの」と同じもの。★ §2.1 の読むだけの本体とは別物 (あちらは書き込みを受け付けない) | 計画再起動の数秒も止められない、という要件が出たとき |
| **両方が独立に書ける (両系・後勝ち)** | PostgreSQL の論理複製は食い違いで止まる (自動の後勝ちには拡張か自前の同期層が要る)。編集の版・タグなどの UNIQUE が衝突する。付随処理 (AI・プッシュ・トリガー・文字起こし) が両側で動く。回線断の間、両側の AI は相手の会話を知らずに答える | **2 拠点に使う人がいて、拠点の間の回線が切れても両側で書き続ける**ことが要件になったとき |
| **ブリッジ (LINE ブリッジ型) で 2 台を同期** | ID が別々になり、返信・既読・編集・削除を全部対応づけることになる。止まらないための仕組みには向かない | 拠点ごとに別の Tealus を動かし、一部の部屋だけ行き来させたいとき (別の用途) |
| **自動切り替え** | 誤った切り替えで 2 台が主系になる方が重い | 切り替えの訓練が定着し、人待ちが問題になったとき |
| **役割を設定ファイルで決める** | 切り替えのたびに書き換える手順が増え、書き換え忘れで「昇格したのに読むだけ」「待機なのに書きに行く」が起きる。DB の状態で決める (§2.1) | — |
| **入口の中継機・クラウドに待機系を置く** | §2 | — |
| **通路に調整役を置く (Tailscale・Headscale など) / 調整役を複数並べる** | 2 台なら真ん中の部品は要らない。Tailscale は業務が有料で採用者の既定にできない。Headscale は複数台を支えていない (§2.2) | 機械が増えたら、クラウドの VM に Headscale を 1 つ |
