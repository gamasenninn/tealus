# 14. CC ブリッジの受け付けを本体へ — agent-server が無くても `@cc-` が届く

> **この文書の立場**: 設計 (2026-11-21 着手、利用者の発案)。issue は #650 (§12)。
> ★ **2026-11-23 に §12 の 1・2 を作った (既定 off)。** `CC_INTAKE=server` を両方の `.env` に書くまで本番の動きは変わらない。★★ **2026-11-24 16:41 に本番を切り替えた** (§12 の 4、取りこぼし 0)。1 週間 (〜12-01) 見ている。
> 下調べは Fable の棚卸し (agent-server がブリッジのためにしていること全部・本体の入口・叩かれている URL・直す docs)、
> 書いたあと別の Fable が監査した (重い 3・中 6・軽 8。すべて反映した。§11 の 1 だけ利用者に聞く)。
> 配達役 (docs/12) とは別の話: こちらは**便を受け箱に入れるところ**、docs/12 は**受け箱から各班へ届けるところ**。

## 1. なぜ (利用者の言葉)

> 「そもそも CC ブリッジはブリッジするだけだから agent サーバー経由じゃなくても成り立つのではと考えた。
> そうすることでユーザは最低限本体だけでブリッジが機能し、内部エージェントを使わなくてもよい選択ができる」(2026-11-21)

- CC ブリッジがしていることは「`@cc-班` を見つける → 班の受け箱 (cc-queue) に 1 行入れる → 取りに来たら渡す」だけで、AI を動かす部分を使っていない。
  agent-server に置いているのは、**最初にそこへ webhook が届いていたから**という経緯だけ
- 今は agent-server が止まると `@cc-` が受け箱に入らない (2026-11-21 利用者「agent-server が止まっても班に届くように」)。本体に移せばこれも解ける
- Tealus の芯「1 台・1 プロセス・同じ入口」に合う。採用者は本体だけで CC ブリッジを使え、社内の AI (アシスタント) を使うかは別に選べる

## 2. 何を変えるか (一言で)

**agent-server がしている「受け付け」(見つける・受け箱に書く・渡す口) を、形を変えずに本体へ移す。** 受け箱のファイル・1 行の形・URL・応答の形は変えない。
だから**配達役・各班の手順 (listen-tealus / handle-tealus)・別の PC の受け手は何も変えなくてよい**。

```
今:   投稿 → 本体 ─(webhook)→ agent-server ─→ cc-queue/<班>.jsonl ─→ 配達役 / 班
                                  └ /agent-api/cc-queue/pending・stream (本体が中継)
後:   投稿 → 本体 ─────────────────────────→ cc-queue/<班>.jsonl ─→ 配達役 / 班
              └ /agent-api/cc-queue/pending・stream (本体が自分で答える。URL は同じ)
      agent-server は AI の仕事だけ (webhook はそのまま受ける)
```

## 4. 入口 — ★ いちばん慎重に

- **webhook (`fireWebhooks`) には乗せない。** `fireWebhooks` は webhook の登録が 0 行だと何もせず戻る (`server/src/services/webhook.mts:167`)。乗せたままでは「本体だけ」にならない
- **新しい入口は「AI へ知らせる」(docs/07 の ③) と同じ場所・同じ on/off で呼ぶ。** `announcePost` (`server/src/services/postEffects.mts`) の ③ が on のときに、同じ投稿で cc の受け付けも呼ぶ
  - ③ が on なのは socket の投稿・転送・音声・`postAsUser` (Bot のテキスト = ルームトリガー・MCP の班・アシスタント) の 4 つ。**今と同じ集合** (LINE・system・ファイルつき・スタンプは起こさない、docs/07 §2)
  - docs/07 の表に列「⑤ cc 受け付け」を足し、**「③ と同じ」をテストで固定**する。★ 表の印は `postingPathSideEffects.test.mts` が読んで突き合わせているので、表とテストの読み取りを同時に直す
  - 1 行は ③ に渡すのと同じ `webhookMessage()` の出力から作る (本文の空白の落とし方・`created_at` の形が今と揃う)。
    webhook を通すと付いてくるもの (部屋名・1 対 1 の部屋名「A ↔ B」の組み立て `webhook.mts:170-192`・送り主の role `:197-201`) は本体で同じものを作る。
    ★ `fireWebhooks` は渡された payload を後から書き換える (room.name・sender.role を足す) ので、同じ物を共有せず写しを使う
- **振る舞いの差** (どれも良い変化。書いておく): webhook の登録に依らなくなる (部屋しばりの webhook や `message.updated` を受けない登録でも起きる)・送り直し (5 秒・15 秒) が要らない・agent-server の短い再起動でも落ちない
- **編集**: `server/src/routes/messages.mts` の `message.updated` を出すところで、編集者 = 投稿者・前後の宛先の差分だけを積む (今の `handleMessageUpdated` と同じ)。
  1 行は DB から足して新規と同じ形にそろえる (§5.2)。写真に最初の説明文を足す編集 (`messages.mts:423`) で cc が起きるのは今と同じ (残す)
- **ゲストの除外**: 送り主の権限は本体が DB で引く。★ 今は「権限が載っていなければ配る」作り (`handler.mts:119`)。本体では必ず引けるので、**引けなければ配らない**側に倒す
- **自分の bot の除外** (自己ループ止め) → §11 の 1 (利用者に聞く):
  - 今: 本番は `ENABLE_CROSS_ROOM_DELEGATION=true`。アシスタントの投稿は**その部屋で仕事中のときと、止まるときの知らせだけ**捨て、それ以外 (別の部屋で行頭に `@cc-x`) は班を起こす
  - 本体はアシスタントの「仕事中」を知らない。**決定 (11-21、§11 の 1)**: 本体の `CC_SKIP_SENDER_IDS` にアシスタントの口座を入れ、**アシスタントは班を起こせない**に変える。
    将来の許可リスト制 (§11 の 1) を足せるよう、送り主で捨てる判定は 1 か所にまとめておく。
    受け箱の実測では、送り主「アシスタント」の便は 104 行あるが全部 2026-08-18〜08-25 で、それ以降は 0
  - 入れ忘れ止め: 本体は起動時に agent-server の `/agent/identity` を 1 回聞けたら、その口座を自動で足す (聞けなければ設定の値だけ。アシスタントを使わない採用者は空のまま)
  - **bot を一律に外さない** (MCP の口座で投稿する班どうしの起こし合いが受け箱に多数あり、使われている)
- 音声: 投稿時の `message.created` は今と同じ扱い。文字起こし後に cc を起こす道は今も無い (作らない、§9)

## 5. 中身

### 5.1 受け箱 (cc-queue)

- 置き場・ファイル名・2,000 行で末尾 80% を残す切り詰め・一時ファイル → rename は**今と同じ**。`CC_QUEUE_DIR` も同じ名前で本体が読む
- 書いたら購読者 (/stream) へも流す (今の `publish` と同じ。部屋のメンバーで絞る)
- ★ 本体は全員のチャットを配っているプロセスなので、**毎回ファイル全体を同期で読まない**: 切り詰めの判定は行数を覚えておく・`/pending` は更新時刻が変わらなければ前の読み取りを使う・読むのは非同期。
  別の PC の配達役 (docs/12 §14) は 5 秒おきに `/pending?events=1` を引く (1 班 1 日 約 17,000 回)

### 5.2 1 行の形

- docs/12 §4.1 の約束 (`id`・`room_id`・`room_name`・`sender {id, display_name, role}`・`content`・`type`・`created_at`・`recipients`) を変えない
- ★ 編集の便も同じ形にそろえる (今は本体が `type`・`created_at`・表示名を載せていないので欠ける)。**足すだけで、消す・名前を変えるはしない**
- `agent-server/__tests__/unit/ccQueueLineContract.test.mts` を本体へ写し、新規・編集の両方で形を固定する

### 5.3 取りに来る口

- 本体に `/agent-api/cc-queue/pending`・`/agent-api/cc-queue/stream`・`/agent-api/agent/cc-projects` を置く。**`/agent-api` の中継の mount より前**に置くので、URL は今と同じ
  (別の PC の `stream_url`・配達役の段階 3・画面の `@` 候補・nginx の設定例は変えなくてよい)
- ★ **本体の口は `CC_INTAKE=server` のときだけ置き、それ以外は今の中継に落とす。** 流れ (/stream) へ配るのは書く人と同じプロセスの中だけなので、
  書くのが agent-server で口が本体 (またはその逆) だと、つながって heartbeat も来るのに便が来ない (静かに外れる)。
  agent-server は `CC_INTAKE=server` のとき `/cc-queue/stream`・`/pending` を **410** で断る (4000 番を直接叩く線が、つながったまま何も来ない状態にならないように)
- 中継より前に置くと本体の `express.json`・`requestLog` より前になる → 新しい口に `requestLog` と `authenticate` を自分で付ける
  (agent-server は「/cc-queue の 401 がどこにも残らなかった」ので requestLog を足した前例)。`authenticate` は `is_active` を見るので無効化された人は弾かれる
- 応答の形 (`count`・`max_age_ms`・`heartbeat_ms`・`events`)・`since` の意味 (見つからなければ残り全部)・15 秒の `{"__hb":1}`・55 分の `__bye` は**今と同じ**
- 部屋のメンバー判定は本体が DB で直接引く (今は agent-server が本体の `/api/rooms` を呼び主の鍵で引いている)
- 本体が止まるとき: `server/src/utils/shutdown.mts` の「予告 → 200ms 待つ → 切る」の予告で、自分の購読者へ `__bye` (`reason: shutdown`) を書く (`notifyGateway` を差し替える)。`gateway-bye` は消す
- 長時間接続の本数は今も本体が中継として持っている数と同じ。切断は減る (今は本体と agent-server のどちらの再起動でも切れる。移した後は本体だけ)

### 5.4 「届きました」の表示

- 今: agent-server がアシスタントの口座で `POST /api/bot/status` (`relayed`) を叩く。アシスタントが部屋にいるときだけ出る・5 秒後に `idle`。
  5 秒後の `idle` は「自分の後に別の表示が出ていたら出さない」で、その番号は agent-server のメモリの中 (`statusSeq.mts`) にある (#542)
- ★ 画面は部屋ごとに表示を 1 つしか持たず、**誰の `idle` でも消す** (`client/src/hooks/useSocketSync.ts` の `handleAgentStatus`、`agent_id` を見ない。確かめた)。
  だから `agent_id` を変えるだけでは、本体の 5 秒後の `idle` がアシスタントの「考え中」を消す (#542 の再発)
- → **番号を本体で持つ。** `agent:status` はすべて本体を通る (`POST /api/bot/status`、`server/src/routes/bot.mts`)。本体で部屋ごとの番号を進め、
  cc の `idle` は「自分の後に誰も出していないときだけ」出す。画面を変えずに済み、古い画面にも効く
- 名前: `agent_id` は `cc:<班>` (画面の宛先候補と同じ形)。表示は `${display_name}: ${message}` なので、表示名を `cc-x` にするなら文面は「届きました。応答をお待ちください」にする (「cc-x: cc-x に届きました」と二重にしない)
- アシスタントのいない部屋でも出るようになる (良い変化。振る舞いの差として書いておく)
- `RELAYED_STATUS = 'relayed'` (client/src/utils/agentStatus.ts) との対は変えない。dashboard の Monitor も `agent:status` を表示するが壊れない

### 5.5 「AI に届きませんでした」の 1 行

- `server/src/services/aiUnreachableNotice.mts` は行頭が `@cc-` の便も「AI に宛てた便」と数えている。**`CC_INTAKE=server` のときだけ** `@cc-` を数えない
  (無条件に外すと、移す前の期間は agent-server が止まっても知らせが出なくなる)。`@アシスタント @cc-x` は名前の判定で先に拾われるので今までどおり出る
- docs/07 §2 の表 #12 の説明と、ファイル頭のコメントも合わせて直す

## 6. ★ 受け箱を書くのは 1 プロセスだけ — 切り替えと戻し

- 切り詰めは読んで書き直すので、本体と agent-server が同時に書くと行が消える (docs/05 の 66 行目)。同じ便を 2 回積むこともある
- **設定だけに頼らない**: 受け箱のフォルダに持ち主の札 `.writer.json` (`{ "process": "server" | "agent-server", "host", "pid", "started_at" }`) を置く
  - ★ **書くたびに札を見る** (起動時だけにすると、戻すとき誰も書かなくなる)。生きている別の持ち主がいれば書かず、error に**便の id** を残す (捨てたことが分かる)。
    持ち主が死んでいれば取る。生死は **PID だけ**で見る (起動時刻は札に書くが読まない。§12 の 1)。自分の役の札は同じ機械なら PID を見ずに取り直す。
    ★ 残る穴: 落ちた別の役の PID を無関係のプロセスが使い回すと、書かずに error を出し続ける (対処は §6.1 の ④)
  - `host` を入れる: Syncthing で受け箱を同期している機械 (docs/setup-cross-machine-syncthing.md) では札も写るので、別の機械の札は生死を見ずに無視する
  - Docker (`docker-compose.full.yml`) では本体と agent-server が受け箱を共有しないので、札は効かないが競合も起きない
- 本体は `CC_INTAKE=server` のときだけ受け付ける。agent-server は `CC_INTAKE=server` のとき受け付けない (同じ名前を両方が読む)
- ★ **版ずれ**: 古い agent-server は札も `CC_INTAKE` も知らないので、本体だけ新しいと両方が書く。→ 本体の既定を on にするのは、
  agent-server の「`CC_INTAKE=server` なら受け付けない」分岐が入った**次の版以降**。upgrade-guide に「本体と agent-server を同じ版で上げる」と書く。
  本体は起動時に agent-server の受け付けの状態を 1 回聞き、両方が受け付ける形なら warn を出す
- **移す手順** (本番): agent-server を `CC_INTAKE=server` で起こし直す (受け付けをやめる・札を手放す) → 本体を同じ値で起こし直す (札を取る) →
  空回しの班に 1 便送って受け箱に 1 行入るのを見る → 全班
- **戻す手順**: 本体を `CC_INTAKE` なしで起こし直す (札を手放す) → agent-server を `CC_INTAKE` なしで起こし直す (書くたびに見るので、本体が先でも後でも次の便で札を取れる)
- 2 つの再起動のあいだ (数秒〜1 分) に来た `@cc-` は受け箱に入らない。移した直後に、その間の投稿のうち本文の行頭に `@cc-` がある便を DB で数え、あれば手で知らせる
  (数える SQL は §6.1 の ⑤)
- ★ **テストが本番の受け箱に書かないこと** (§10)

### 6.1 本番の手順書 (2026-11-24、利用者「tealus サーバーだけで運用するには」)

2 段に分ける。**1 段目だけなら失うものは無い**。1 週間見てから 2 段目。

**1 段目: 受け付けを本体へ** (agent-server は動かしたまま)

0. 前提: 本体と agent-server が同じ版 (§6 の版ずれ)。4000 番を直接叩く試しの線 (§11 の 4) を止めてある
1. `agent-server/.env` と `server/.env` に `CC_INTAKE=server`。`server/.env` は書き換えると権限が広がるので `icacls` で絞り直す
   - §7 の `CC_*` の値と `cc-aliases.json` を agent-server から本体へ写す (本番は 2026-11-24 時点で写すもの無し。写し忘れの warn は切り替えた後にしか出ない)
2. agent-server を起こし直す (時刻 T1 を控える)。札を手放し、`/pending`・`/stream` は 410
3. すぐ続けて本体を起こし直す (時刻 T2)。札を取る。起動のログに受け付けの開始
4. 確かめる: 札 `.writer.json` の `process` が `server` / 試しの部屋から `@cc-` を 1 便 → 受け箱に 1 行・配達役が届ける /
   HTTP で取り寄せる配達役 (段階 3) が本体から取れている (★ `/pending` の 200 は本体のログに出ない。見るのは配達役の側の
   `~/.tealus/courier/events-YYYYMMDD.jsonl` と管理画面「AIの班」の鼓動、本体のログに `[http-denied]` が無いこと、
   同じ鍵で `/agent-api/cc-queue/pending?project=X` が 200・agent-server の 4000 番の直叩きが 410)
   - ★ 本体のログに「受け箱の持ち主が別のプロセス (… pid=N) のため書いていません」が出たら: 札の `pid` のプロセスが本当に
     agent-server か確かめる (PID だけで見ているため、§6)。別物なら `.writer.json` を消すと次の便で本体が取る
5. T1〜T2 の間の `@cc-` を数える。あれば相手の班へ手で知らせる:
   ```sql
   SELECT m.id, r.name, m.created_at, left(m.content, 60)
     FROM messages m JOIN rooms r ON r.id = m.room_id
    WHERE m.created_at BETWEEN :t1 AND :t2
      AND m.is_deleted = false AND m.type = 'text'
      AND m.content ~ '(^|\n)\s*@cc-'
    ORDER BY m.created_at;
   ```
   (行頭の判定は宛名の読み取りより広い。拾いすぎは目で落とす。編集で足された宛先は数えない)
6. 1 週間、取りこぼし 0 を見る → §12 の 5

戻す: 両方の `.env` から `CC_INTAKE` を消し、本体 → agent-server の順に起こし直す。
