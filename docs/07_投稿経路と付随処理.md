## 5. これから

**素直な統合はしない。** 1 つの関数に寄せて全部同じにすると、意図的に外してあるもの (LINE で AI が動かない、
system メッセージで議事録を作りに行かない) まで揃ってしまい、要件が壊れる。

```
第 1 段  1 つの入口 (postAsUser) を作り、経路を 1 本ずつ移す。
        移すときに「いまの穴」を宣言として書く (例: 通常アップロードは「③ は付けない」と明示)
        → 挙動は完全に同じ。変わるのは「無言」が「宣言」になることだけ
第 2 段  宣言を 1 つずつ見て、意図か忘れかを判断する。直すものだけ直す
```

**第 1 段は 1 本だけ済んでいる** —— `postAsUser` (#382 で作った。#5 の Bot API テキスト投稿がこれを通る)。
残り 17 本は未着手。

### 5.1 段階 1 の形 (2026-10-01): INSERT はそのまま、付随処理だけ 1 つの入口へ

★ 経路ごとに **INSERT の形が違いすぎる** (添付・サムネイル・文字起こし・LINE の保存) ので、`postAsUser` に全部を寄せるのはやめた。
**付随処理 4 つだけを `announcePost` (`server/src/services/postEffects.mts`) に寄せる。**

```
announcePost({
  roomId,
  emit:    { 配信する中身 },                                   ① 必須
  push:    { kind: 'machine', post } | { kind: 'human', … } | { kind: 'off', reason },   ②
  webhook: { kind: 'on', payload } | { kind: 'off', reason },  ③
  preview: { kind: 'on', … }       | { kind: 'off', reason },  ④
})
```

- ★ **4 つとも必須の欄**。付けないものも `{ kind: 'off', reason: '…' }` と理由を書かないと型が通らない = 「無言」が「宣言」になる
- ★ **送る中身と待ち方は、移す前と同じにする** (段階 0 のテストは「呼ばれたか」しか見ないので、移す経路ごとに**中身を固定するテストを先に足す**)
- ★ 呼ぶ位置は、今と同じ例外処理の中 (commit の後) に置く
- 試しに #6 #7 (ボットの画像・ファイル) から移し、読みやすく・安全になったかを見てから続けるかを決める。#1 (人の投稿) は最後
- ★ 入口の順番は **① 配信 → ② 通知 → ③ AI 通知 → ④ プレビュー**。#8 (音声) だけ移す前は「AI 通知 → 通知」だった。
  経路ごとに順番を選べる仕組みは作らず、**入口の順に揃えた** (2026-10-01 利用者判断)。人は通知を待たないので差は無く、
  機械は通知 (部屋の設定を DB に聞く) を待ってから AI 通知を投げる分、数 ms 遅れる
- 移した経路 (2026-10-01): #2 #3 #4 #5 #6 #7 #8 #10 #11 #12 #12'。(2026-10-02): #1 と #13〜#18 (LINE)。**付随処理のある 17 本はすべて入口を通る**。#9 (REST) は付随処理が 1 つも無いので移さない
- ★ #13 (LINE のテキスト) も移す前は「配信 → プレビュー → 通知」で、入口の順に揃えた (2026-10-02 利用者判断。どちらも待たずに投げるので差は無い)。
  LINE の音声は文字起こしの起動を入口の後に置いた (#8 と同じ並び)
- LINE は呼び出し側から io を渡す作り (Option D) なので、入口に `io` の欄を足した (省略すると getIo()、null なら配信しない = 移す前の LINE と同じ)
- 人の通知の失敗 (reject) は入口で記録して続ける (2026-10-02 まで try/catch で、reject は握れていなかった。LINE は移す前から捨てていた)
- #1 (人の投稿) を移すときに ④ プレビューの「付ける」形 `{ kind: 'on', messageId, text }` を足した (待たずに投げ、失敗は捨てる = 移す前と同じ)。
  #1 は通知とプレビューに**空白を落とす前**の本文、配信 (DB) と AI 通知に**落とした後**の本文を渡している。揃えてはいない (挙動を変えないため)
- ★ system メッセージ 5 か所は、付けない理由が同じなので `SYSTEM_MESSAGE_EFFECTS` (postEffects.mts) を共有する

**この表は手で保守すると腐る。** 第 1 段が全経路で終われば宣言がコードに書かれるので、
表はそこから生成できるようになる。そこが本来の着地点。

★ 2026-10-02: 生成はせず、**突き合わせ**にした。§2 の表の ①〜④ の印を、`__tests__/socket/postingPathSideEffects` の最後のテストが
