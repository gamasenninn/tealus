# 会話モード設計 — 組織記憶に入れないための入口

**状態**: 設計のみ。実装はまだ (#389)。
**起点**: 業務メモ 2026-08-24 02:51「会話モードを検討する」 → 聞き直して
「**リアルタイムチャットのイメージ。普通のチャット機能だが、音声でのやりとりを主体とする**」。

**先に読むこと**: [`tealus_voice_ui_wireframe.md`](tealus_voice_ui_wireframe.md)
(音声メッセージの既存設計。「まず話そう、整えるのはあとでいい」の原則はそこにある)。
本書は **その原則が効かない最初のケース**を扱う (§6)。

---

## 1. 何を作るのか — 新しい音声機能ではない

調査の結論を先に書く。

> **声で往復する部品は、すでに全部ある。会話にならないのは、真ん中が 40 秒だからだ。**

だから本件は「音声機能を作る」仕事ではなく、**既にある部品を 1 つのルームに結線する**仕事になる。
増える機能は「**会話専用ルームという場所**」と「**そこでの既定設定**」だけ。

### 1.1 ★ 正確には「結線」ですらない — 場所によっては今日そのまま動く

**当初この節に「結線する仕事」と書いたが、それも重い。** コードを読み直して確定した。

文字起こしは `handler.mts:319` で `message.content` に差し替えられ、
**テキストと完全に同じ `dispatch()` を通る**。止めているのは**メンションの門だけ**。

```
needsMention = response_mode === 'mention' ? true
             : response_mode === 'all'     ? false
             : /* auto */ memberCount > 2;      // dispatcher.mts:240
```

| 場所 | メンション | 音声だけで AI が動くか |
|---|---|---|
| **アシスタントとの 1 対 1** | `auto` かつ 2 人 → **不要** | **動く。設定変更ゼロ** |
| `response_mode: 'all'` のルーム | 不要 | 動く。設定 1 行 |
| 3 人以上の通常ルーム | 必要 | **動かない** (§8 の穴) |

**声でメンションすることはできない。** `mention.mts:13` の判定は `^@アシスタント` で
**リテラルの `@`** を要求するが、文字起こしは `@` を書かない。
だから音声会話が成立するのは「メンションできるから」ではなく
**「メンションが要らない場所だから」**である。ここは向きを間違えやすい。

→ **段 1 は「作る」ではなく「置いて、押して話してみる」になる** (§9)。

## 1.2 ★ 何のための会話モードか — 捨てるためではなく、昇格させるため

**2026-08-24 の議論で目的が確定した。ここが本書で一番効く節。**

会話モードは「声で話せる機能」ではない。**組織記憶に入れないための入口**である。

### 1.2.1 なぜ「入れない入口」が要るか

Tealus のルームは記録ではなく**原料**である。議事録・organon・語彙が下流でこれを読む。
さらに agent は**毎ターン履歴を読む** (§2.2.1 の実測で input が毎回ほぼ 96k で一定)。

つまり **捨てるべき会話が残ると、残すべき会話の質が落ちる**。
天気や単位換算が混ざると、業務の文脈が薄まり、固定費だけが増える。

※ ただし正確には、**辞書の自動学習は「人が文字起こしを直したとき」しか動かない**ので、
雑談が直接辞書に流れ込むわけではない。効くのは主に「毎ターン読まれる履歴」の側。

### 1.2.2 ★ 昇格が無いなら作らない

**捨てるだけなら、それは ChatGPT である。** 現場はより速く賢いものを既に手元に持っている。
Tealus にしかできないのは、捨てる前提で話した中から**良かった 1 つだけを本番ルームへ送る**ことだ。

```
使い捨てで壁打ち  →  良かった 1 つを選ぶ  →  業務ルームへ送る
（残らない）                                 （組織記憶になる）
```

**したがって「昇格の導線」は付属機能ではなく成立条件とする。**
昇格が無い会話モードは作らない。

これは看板と矛盾しない。「会話が組織の記憶になる」に逆行するように見えるが、逆である。
**捨てられるからこそ、残っているものを信用できる。**

### 1.2.3 主用途は雑談ではなく「下書き・壁打ち」

効く順に並べる。**雑談は一番下**である。

| | 場面 | なぜ効くか |
|---|---|---|
| 1 | **下書き・壁打ち** | 3 往復して最後の 1 文だけ本番へ。途中は誰も見なくていい |
| 2 | **人に見せる前の確認** | 間違えた過程が残らないと、人は気軽に聞ける |
| 3 | **試し撃ち** | 動作確認で本番ルームを汚さない |
| 4 | **言いにくい相談** | ルームだと他メンバーに見え、DM でも履歴に残る |
| 5 | ~~雑談・その場の調べもの~~ | **弱い。§6.0 を見ること** |

### 1.2.4 分かれるのは「人」ではなく「場面」

「要る人と要らない人が分かれる」ように見えるが、**同じ人が場面で使い分ける**。
よって **利用者ごとの出し分け設定は作らない。切り替えられればよい** (§10)。

| 段 | 段 0 実測 (n=2) | §2.2 の事前値 |
|---|---|---|
| 音声 → 文字起こし | **2.0 / 3.7 秒** | 2.8 秒 — **一致** |
| 文字 → 応答 | **18.7 / 32.5 秒** | 31.4 秒 (n=1) — 同じ桁 |
| 全体 | **22.5 / 34.5 秒** | — |
| input tokens | **約 96,000** (2 回とも) | 93,931 — **ほぼ同じ** |

**§2.4 の見立ては当たっていた。** 音声まわりは速く、遅いのは真ん中だけ。
そして input が毎回ほぼ 96k で一定なのは、**発話の長さに関係なく固定費が乗っている**証拠。
削るなら §6.2-1 (会話ルームに辞書を注入しない) から、という順序を支持する。

**測り方の失敗を 1 つ記録する。** ログの自動集計で「10.1 秒」という値が出たが、
**別ルームの受信と このルームの応答を取り違えたペアリング**だった。生ログで破棄した。
往復を測るときは、**受信と応答が同じルームか**を必ず確認すること。

### 2.3 標本の弱さを明記する

- LLM 経路の往復は **n=1**。「40 秒かかる」は 1 例の観測であって、分布は分かっていない。
- 直近 7 日のログに完了往復は **5 件しかなく、5 件とも議事録作成のような重い依頼**だった
  (87 / 113 / 152 秒)。**短い会話らしい往復は、そもそも誰もやっていない。**
- したがって「会話は遅い」は**現状の使われ方の外側の話**であり、
  実装後にもう一度、本番の文脈で測り直すこと (§7-5)。

### 2.4 遅さの出どころ

`input=93,931 tokens`。system prompt に固定で注入されるものだけで約 78KB ある
(既定 prompt 8.5KB + ルーム固有 3.2KB + ルーム CLAUDE.md 1.1KB + 辞書 65KB)。
さらに「道具を使うな」と書いたのに `get_messages` を呼んでいる。

**律速は毎ターン読ませている文脈量であって、モデルでも音声でもない。**

## 4. 会話専用ルームにする理由

既存ルームに「会話モード」を足す案は採らない。

- 既存ルームは **応答の振る舞いが業務で固まっている** (朝礼は議事録、社内DB検索は検索)。
  `response_mode` を触ると、そのルームの既存の使われ方を壊す。
- 会話モードは **未知の失敗をする**。壊れたときに、**その 1 ルームの中で止まる**方がよい。
- 専用ルームなら、既定設定をそのルームだけに置ける (`room_settings.json` はルーム単位)。

**トランシーバー履歴ルームを流用する案も採らない。** あそこは現場の業務無線が流れる本番で、
AI が喋り出すと業務の邪魔になる。会話モードは**別の場所**に置く。

## 5. 話しかけ方は「押して話す」

既存の PTT (mediasoup) をそのまま使う。ハンズフリー (発話検知) は**作らない** (§10)。

理由:

- **実装済みの仕組みがそのまま使える** (`useTransceiver.ts`)。新規実装がゼロ。
- 農機具屋の現場は騒音があり、**発話検知は周囲の会話・機械音を拾う**。
  押している間だけ拾う方が、現場では確実。
- 「いつ切れたか」を人が決めるので、**発話の切れ目を推定する仕組みが要らない**。

## 6. ★ 速さは後回しにする — その判断の中身

**決定: 遅いまま繋げる。速くするのは、繋がってから測って決める。**

理由は 2 つある。**後から足した 2 つ目の方が強い。**

**理由 1: どこを削るべきかが、まだ分かっていない。**
§2.3 のとおり短い往復の標本は小さい。この状態で「辞書注入を外す」「道具を減らす」と
決めると、**測る前に前提を作ってしまう**。

**理由 2 (2026-08-24 追加): 主用途を「下書き・壁打ち」に置いたから待てる。**
考えている最中の 20〜30 秒は待てる。§1.2.3 のとおり主用途は雑談ではない。

### 6.0 ★ この判断は主用途に依存している (崩れる条件)

**主用途が雑談に戻った瞬間、§6 の決定は崩れる。**

議事録を作らせるなら 40 秒待てる。**天気を聞くのに 30 秒待つ人はいない。**
スマホで調べた方が速い。§2.2.1 の実測は 22.5 / 34.5 秒で、これは雑談には遅すぎる。

```
主用途 = 下書き・壁打ち  →  速さは後回しでよい   ← 現在の決定
主用途 = 雑談・即答      →  速さが最優先になる   ← §6.2 を先にやる話になる
```

**両方は選べない。** 用途を変えるときは、この節に戻って §6 の決定を引き直すこと。

### 6.1 既存設計の原則は、ここでは効かない

`tealus_voice_ui_wireframe.md` は遅延にすでに答えを出している。

> **遅延は弱点ではなく進行中として見せる** / **まず話そう。整えるのはあとでいい。**

これは**メッセージ**には効く。音声を先に送れて、後から文字になり、整う。
待っている間も「送れている」。

**しかし会話では効かない。** 会話における 40 秒は「進行中」に見えない。ただの無言になる。
相手が考えているのか、壊れたのか、聞こえなかったのかが**区別できない**
(これは docs/05 の「沈黙が 2 通りに読める」と同じ形)。

**したがって、繋げる第 1 段では速さの代わりに「今どうなっているか」を必ず出す** (§7-2)。
無言で待たせない。

### 6.2 速くするときの候補 (今は決めない)

測ってから選ぶ。順に並べてあるが、この順で正しいという根拠はまだない。

1. 会話ルームの `light_prompt.md` を最小にする (辞書 65KB を会話ルームには注入しない)
2. 道具を絞る (会話では `get_messages` すら要らない場面が多い)
3. 応答を待たずに読み上げを始める (最初の文が出た時点で喋り出す)
4. ルール即答の範囲を広げる (挨拶が 24 ミリ秒で返っている事実を使う)

**音声対話専用 API は候補に入れていない。** 業務会話の音声そのものが外部に出るため、
データ主権の看板と正面から衝突する。使うなら別途、明示的な判断が要る。

## 7. 外せない条件 (実装時のチェックリスト)

1. **既存ルームの振る舞いを 1 つも変えない。** 変更は会話専用ルームの中だけで閉じる。
2. **無言で待たせない。** 応答生成中は、それが見える状態を出す (§6.1)。
   何も出さないのは「壊れた」と区別が付かない。
3. **割り込みで読み上げが止まる。** 再生中に押して話し始めたら TTS を止める。
   止まらないと、自分の声と AI の声が重なって会話にならない。
4. **音声原本を消さない。** 既存の音声メッセージと同じく、原本は残し文字だけ直せる
   (`tealus_voice_ui_wireframe.md` §6-7 の約束)。
5. **★ 繋げた直後に、同じ計器で測り直す。**
   §2.2 の 4 段を、会話ルームの本番文脈で測る。
   §2.3 のとおり今の標本は n=1〜5 なので、**実装前の数字を「基準」と呼ばない**。

| 穴 | 中身 | なぜ受け入れるか |

### 9.1 ★ なぜ昇格が先か (2026-08-24 に順序を入れ替えた)

当初は「まず保存期間で試す」と考えたが、**実装コストを調べたら逆だった**。

```
昇格     forwarded_from 付きの転送が既に実装済み   → 実装ゼロ
保存期間 該当する仕組みが無い                     → 新規実装が要る
```

しかも昇格は **§1.2.2 の成立条件そのもの**である。
「昇格が無いなら作らない」と決めた以上、**一番安い手段でその条件を先に検証する**のが筋。

**段 5 を飛ばして段 6 に行かないこと。** 飛ばすと、また測る前に前提を作ることになる。

## 10. 作らないもの (明示的に範囲外)

  UI が本当に要るかは、使ってみてから決める
- **★ 利用者ごとの出し分け設定** — §1.2.4。分かれるのは人でなく場面なので、
