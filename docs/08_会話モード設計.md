## 1. 何を作るのか — 新しい音声機能ではない

調査の結論を先に書く。

> **声で往復する部品は、すでに全部ある。会話にならないのは、真ん中が 40 秒だからだ。**

だから本件は「音声機能を作る」仕事ではなく、**既にある部品を 1 つのルームに結線する**仕事になる。
増える機能は「**会話専用ルームという場所**」と「**そこでの既定設定**」だけ。

### 1.1 ★ 正確には「結線」ですらない — 場所によっては今日そのまま動く

**当初この節に「結線する仕事」と書いたが、それも重い。** コードを読み直して確定した。

文字起こしは `handler.mts:319` で `message.content` に差し替えられ、
**テキストと完全に同じ `dispatch()` を通る**。止めているのは**メンションの門だけ**。

```
needsMention = response_mode === 'mention' ? true
             : response_mode === 'all'     ? false
             : /* auto */ memberCount > 2;      // dispatcher.mts:240
```

| 場所 | メンション | 音声だけで AI が動くか |
|---|---|---|
| **アシスタントとの 1 対 1** | `auto` かつ 2 人 → **不要** | **動く。設定変更ゼロ** |
| `response_mode: 'all'` のルーム | 不要 | 動く。設定 1 行 |
| 3 人以上の通常ルーム | 必要 | **動かない** (§8 の穴) |

**声でメンションすることはできない。** `mention.mts:13` の判定は `^@アシスタント` で
**リテラルの `@`** を要求するが、文字起こしは `@` を書かない。
だから音声会話が成立するのは「メンションできるから」ではなく
**「メンションが要らない場所だから」**である。ここは向きを間違えやすい。

→ **段 1 は「作る」ではなく「置いて、押して話してみる」になる** (§9)。

## 1.2 ★ 何のための会話モードか — 捨てるためではなく、昇格させるため

**2026-08-24 の議論で目的が確定した。ここが本書で一番効く節。**

会話モードは「声で話せる機能」ではない。**組織記憶に入れないための入口**である。

### 1.2.1 なぜ「入れない入口」が要るか

Tealus のルームは記録ではなく**原料**である。議事録・organon・語彙が下流でこれを読む。
さらに agent は**毎ターン履歴を読む** (§2.2.1 の実測で input が毎回ほぼ 96k で一定)。

つまり **捨てるべき会話が残ると、残すべき会話の質が落ちる**。
天気や単位換算が混ざると、業務の文脈が薄まり、固定費だけが増える。

※ ただし正確には、**辞書の自動学習は「人が文字起こしを直したとき」しか動かない**ので、
雑談が直接辞書に流れ込むわけではない。効くのは主に「毎ターン読まれる履歴」の側。

### 1.2.2 ★ 昇格が無いなら作らない

**捨てるだけなら、それは ChatGPT である。** 現場はより速く賢いものを既に手元に持っている。
Tealus にしかできないのは、捨てる前提で話した中から**良かった 1 つだけを本番ルームへ送る**ことだ。

```
使い捨てで壁打ち  →  良かった 1 つを選ぶ  →  業務ルームへ送る
（残らない）                                 （組織記憶になる）
```

**したがって「昇格の導線」は付属機能ではなく成立条件とする。**
昇格が無い会話モードは作らない。

これは看板と矛盾しない。「会話が組織の記憶になる」に逆行するように見えるが、逆である。
**捨てられるからこそ、残っているものを信用できる。**

### 1.2.3 主用途は雑談ではなく「下書き・壁打ち」

効く順に並べる。**雑談は一番下**である。

| | 場面 | なぜ効くか |
|---|---|---|
| 1 | **下書き・壁打ち** | 3 往復して最後の 1 文だけ本番へ。途中は誰も見なくていい |
| 2 | **人に見せる前の確認** | 間違えた過程が残らないと、人は気軽に聞ける |
| 3 | **試し撃ち** | 動作確認で本番ルームを汚さない |
| 4 | **言いにくい相談** | ルームだと他メンバーに見え、DM でも履歴に残る |
| 5 | ~~雑談・その場の調べもの~~ | **弱い。§6.0 を見ること** |

### 1.2.4 分かれるのは「人」ではなく「場面」

「要る人と要らない人が分かれる」ように見えるが、**同じ人が場面で使い分ける**。
よって **利用者ごとの出し分け設定は作らない。切り替えられればよい** (§10)。

### 2.3 標本の弱さを明記する

- LLM 経路の往復は **n=1**。「40 秒かかる」は 1 例の観測であって、分布は分かっていない。
- 直近 7 日のログに完了往復は **5 件しかなく、5 件とも議事録作成のような重い依頼**だった
  (87 / 113 / 152 秒)。**短い会話らしい往復は、そもそも誰もやっていない。**
- したがって「会話は遅い」は**現状の使われ方の外側の話**であり、
  実装後にもう一度、本番の文脈で測り直すこと (§7-5)。

### 2.4 遅さの出どころ

`input=93,931 tokens`。system prompt に固定で注入されるものだけで約 78KB ある

さらに「道具を使うな」と書いたのに `get_messages` を呼んでいる。

**律速は毎ターン読ませている文脈量であって、モデルでも音声でもない。**

## 4. 会話専用ルームにする理由

既存ルームに「会話モード」を足す案は採らない。

- 既存ルームは **応答の振る舞いが業務で固まっている** (朝礼は議事録、社内DB検索は検索)。
  `response_mode` を触ると、そのルームの既存の使われ方を壊す。
- 会話モードは **未知の失敗をする**。壊れたときに、**その 1 ルームの中で止まる**方がよい。
- 専用ルームなら、既定設定をそのルームだけに置ける (`room_settings.json` はルーム単位)。

**トランシーバー履歴ルームを流用する案も採らない。** あそこは現場の業務無線が流れる本番で、
AI が喋り出すと業務の邪魔になる。会話モードは**別の場所**に置く。

### 4.1 ★ 転回 (2026-09-05) — 「専用ルーム」から「開けるルームを選べる」へ

**利用者決定**: 会話モードは**ルームごとに開ける / 開けないを選ぶ**。全ルーム解放にはしない。

上の 3 つの理由を、**Realtime 経路で 1 つずつ生死判定した**。全部が死んだわけではない。

| §4 の理由 | 判定 | 中身 |
|---|---|---|
| ① 既存ルームは応答の振る舞いが業務で固まっている | ★ **前提が消えた** | 旧設計で壊れたのは、会話モードが**同じ dispatch 経路を共有する**から (`response_mode` を触る)。**Realtime 経路は dispatch を 1 度も通らない** — 既存ルームで開いても、そのルームの agent 応答は 1 ビットも変わらない。§7-1 は経路が分かれていることで自動的に守られる |
| ② 未知の失敗はその 1 ルームで止まる方がよい | ★★ **生きる** | 失敗の形が変わっただけ (dispatch 事故 → 誤発話・道具の誤爆・コスト・transcript の混入)。★★★ **これが「開けるルームを選べる」の根拠**。既定 false で、admin が明示的に開けたルームにだけ出る。全ルーム解放にしない理由はこの理由②が生き残っているから |
| ③ 既定設定をそのルームだけに置ける | ★ **形を変えて生きる** | `room_settings.json` の `response_mode` ではなく、`rooms.voice_conversation_enabled` 列 (+ 将来はルーム別 instructions) になる |

★ ★ **トランシーバー履歴ルームを避ける判断も生きる。** 「そのルームでは開けない」で
そのまま表現できる (既定 false なので、**何もしなければ開かない**)。

★ **したがって §4 の見出し「会話専用ルームにする理由」は、正確には
「会話モードを勝手に増やさない理由」だった。** 専用ルームは手段で、理由②が目的である。

## 5. 話しかけ方は「押して話す」

既存の PTT (mediasoup) をそのまま使う。ハンズフリー (発話検知) は**作らない** (§10)。

理由:

- **実装済みの仕組みがそのまま使える** (`useTransceiver.ts`)。新規実装がゼロ。
- 農機具屋の現場は騒音があり、**発話検知は周囲の会話・機械音を拾う**。
  押している間だけ拾う方が、現場では確実。
- 「いつ切れたか」を人が決めるので、**発話の切れ目を推定する仕組みが要らない**。

### 5.1 ★ Realtime 経路でも「押して話す」 (2026-09-05)

**訂正は要らなかった。** Realtime API は自動で喋り出す (VAD) 仕組みだと思われがちだが、
**手動ターン制御ができる**。公式ドキュメントで確認した:

```
turn_detection: null          ★ サーバ側の発話検知を切る = 押して話す
input_audio_buffer.commit     離したときに送る (話し終わりを人が決める)
response.create               続けて送る = ここから応答が始まる
response.cancel               ★ 割り込み。AI が喋っている最中に押したら送る
```

★ **これで §5 の理由が 3 つとも生き残る**。加えて 2 つ得をする:

- ★★ **基準①の起点と一致する** (§7.1)。「押して話し終えてから」を計器で拾える。
  VAD だと「いつ話し終わったとモデルが判断したか」が観測できず、測る起点が消える
- ★★ **基準③ (割り込み) が決定的に満たせる**。押した瞬間に `response.cancel` を送って
  ローカルで消音する。VAD の推定に頼らないので「止まらないことがある」が原理的に無い
- ★ AI 発話中はマイクが無効なので、エコー対策もほぼ要らない

★ **崩れる条件** (§6.0 と同じ形で書いておく): **押して話すの会話感が悪ければ VAD を試す。**
そのときは §5 に戻って理由を引き直すこと。「押すのが面倒」が実機で出たら、それは
§5 の「現場の騒音より確実性を採る」を**現場でない場所に当てはめていた**ということになる。

## 6. ★ 速さは後回しにする — その判断の中身

**決定: 遅いまま繋げる。速くするのは、繋がってから測って決める。**

理由は 2 つある。**後から足した 2 つ目の方が強い。**

**理由 1: どこを削るべきかが、まだ分かっていない。**
§2.3 のとおり短い往復の標本は小さい。この状態で「辞書注入を外す」「道具を減らす」と
決めると、**測る前に前提を作ってしまう**。

**理由 2 (2026-08-24 追加): 主用途を「下書き・壁打ち」に置いたから待てる。**
考えている最中の 20〜30 秒は待てる。§1.2.3 のとおり主用途は雑談ではない。

### 6.0 ★ この判断は主用途に依存している (崩れる条件)

**主用途が雑談に戻った瞬間、§6 の決定は崩れる。**

議事録を作らせるなら 40 秒待てる。**天気を聞くのに 30 秒待つ人はいない。**
スマホで調べた方が速い。§2.2.1 の実測は 22.5 / 34.5 秒で、これは雑談には遅すぎる。

```
主用途 = 下書き・壁打ち  →  速さは後回しでよい   ← 現在の決定
主用途 = 雑談・即答      →  速さが最優先になる   ← §6.2 を先にやる話になる
```

**両方は選べない。** 用途を変えるときは、この節に戻って §6 の決定を引き直すこと。

### 6.1 既存設計の原則は、ここでは効かない

`tealus_voice_ui_wireframe.md` は遅延にすでに答えを出している。

> **遅延は弱点ではなく進行中として見せる** / **まず話そう。整えるのはあとでいい。**

これは**メッセージ**には効く。音声を先に送れて、後から文字になり、整う。
待っている間も「送れている」。

**しかし会話では効かない。** 会話における 40 秒は「進行中」に見えない。ただの無言になる。
相手が考えているのか、壊れたのか、聞こえなかったのかが**区別できない**
(これは docs/05 の「沈黙が 2 通りに読める」と同じ形)。

**したがって、繋げる第 1 段では速さの代わりに「今どうなっているか」を必ず出す** (§7-2)。
無言で待たせない。

### 6.2 速くするときの候補 (今は決めない)

測ってから選ぶ。順に並べてあるが、この順で正しいという根拠はまだない。

1. 会話ルームの `light_prompt.md` を最小にする (辞書 65KB を会話ルームには注入しない)
2. 道具を絞る (会話では `get_messages` すら要らない場面が多い)
3. 応答を待たずに読み上げを始める (最初の文が出た時点で喋り出す)
4. ルール即答の範囲を広げる (挨拶が 24 ミリ秒で返っている事実を使う)

**音声対話専用 API は候補に入れていない。** 業務会話の音声そのものが外部に出るため、
データ主権の看板と正面から衝突する。使うなら別途、明示的な判断が要る。

## 7. 外せない条件 (実装時のチェックリスト)

1. **既存ルームの振る舞いを 1 つも変えない。** 変更は会話専用ルームの中だけで閉じる。
   ★ (2026-09-05) **Realtime 経路は dispatch を 1 度も通らないので、この条件は経路が
   分かれていることで自動的に守られる。** 既存ルームで開いても agent 応答は変わらない (§4.1)。
2. **無言で待たせない。** 応答生成中は、それが見える状態を出す (§6.1)。
   何も出さないのは「壊れた」と区別が付かない。
3. **割り込みで読み上げが止まる。** 再生中に押して話し始めたら TTS を止める。
   止まらないと、自分の声と AI の声が重なって会話にならない。
4. **音声原本を消さない。** 既存の音声メッセージと同じく、原本は残し文字だけ直せる

   直せることを守っていた。Realtime では (a) 原本が存在せず (b) transcript を作るのも
   OpenAI で、戻って直す経路が無い。
   → ★★ **代わりに transcript を残す。** 昇格に要るのは**テキスト**であって原本ではない
   (§1.2.2 の「良かった 1 つを送る」の 1 つは文である)。**ブラウザ側の並行録音は作らない** (§10)。
   → ★ **この条件は既存の音声メッセージ経路の約束としてはそのまま生きる。**
5. **★ 繋げた直後に、同じ計器で測り直す。**

### 12.2 方式 — 関数呼び出し。リモート MCP は採らない

```
★★ 関数呼び出し方式    ★ こちらのプログラムが叩く
                     → ★★ 今ある道具がそのまま使える / ★ 外から入る口は不要
```

★★ **採るのは関数呼び出し方式。** 公開の口を開けずに済むことより、

| **R3** | 出口: transcript から 1 つ選んで業務ルームへ送る (昇格) | 昇格が 1 回通る (§1.2.2 の成立条件) |

★ **R0 と R2 の後に、実機で触ってもらって判定を仰ぐ。**

★★ **2026-09-05 時点: R0 / R1 / R2 は通った** (実測は §12.7)。★ **R3 (昇格) が残っている。**
★ ただし §1.2.2 が「**昇格が無いなら作らない**」を成立条件にしているので、
**R3 が通るまでは「会話モードが出来た」と書かない**こと。今あるのは「話せるところまで」である。
★★ **R0 の最初の関門は「現場のネットワークから OpenAI へ WebRTC が通るか」** —— これはテストで
固定できない。通らなければ WebSocket 経由という逃げ道はあるが、遅くなるので① が危うくなる。

### 12.6 測定の仕込み (§7-5「同じ計器」を担保する)

`performance.now()` を基準に client 側でイベントを積み、`/voice-chat/log` で回収する。
★★ **道具の有無で層別できる形にする** (§7.1 のとおり ① と ④ は同じターンで衝突する)。

| 基準 | 計器 |
|---|---|
| ① 2 秒 | 離した時刻 → **AI 音声の有音立ち上がり**。★ `AnalyserNode` で自前検知する (OpenAI のイベント名に依存しない計器にする) |
| ② 3 往復 | ターンの通番と各ターンの成否 / 切断・エラー |
| ③ 割り込み | 押した時に AI が喋っていたか + cancel から無音までの ms |
| ④ さっきの話 | 道具の呼び出し (有無・名前・所要。サーバ側 JSONL と `session_id` で突合) + **transcript 全文**。★ 通じたかは**人が読んで判定する** (自動化しない) |

★ **集計は §2.2 の段分けと同じ表の形にする。** そうしないと「同じ計器で測り直す」にならない。

### 12.7 ★ 実測 (2026-09-05、事務所。**1 セッションの結果であって「基準」ではない**)

**R0〜R2 を通した後の実測。** §2.3 / §7-5 のとおり、この数字を「基準」と呼ばない。

```
★ 母集団  1 セッション / 6 往復 / 割り込み 5 回 / 道具の呼び出しは別セッション
★ 場所    事務所のネットワーク。★★ 現場 (各拠点) では測っていない
```

| 基準 | 結果 | 実測 |
|---|---|---|
| ① 2 秒以内 | ★ **6/6** | 中央値 **0.71 秒** / 最大 1.36 秒 |
| ② 3 往復 | ★ **達成** | 6 往復、落ちなし |
| ③ 割り込める | ★ **達成** | 中央値 **113ms** で `output_audio_buffer.cleared` (n=4) |
| ④ さっきの話 | ★ **達成** | 別セッションで `get_messages` により業務メモを引いて要約 |

★ **エラー 0 件。**

★★ **③ の n=4 の理由を書いておく。** 割り込みは 5 回記録されたが、**1 回は鳴っていない時に押した**
もので (`was_playing=false`)、その 22 秒後の `stopped` は次の応答が普通に終わっただけ。
**分母に入れると 22 秒が混じって中央値が壊れる。** 割り込みを測るときは
「押した時に本当に鳴っていたか」で分母を作ること。

★ **①で予想が外れた点**: 道具を呼んだターンの方が速かった (別セッション、0.84 秒 vs 0.91 秒)。
指示どおり「確認しますね」と**先に喋ってから**道具を呼ぶため。道具自体も 10〜241ms で、
心配していた MCP の往復は律速ではなかった。

★ **まだ言えないこと**: 現場のネットワーク / 長い会話 (10 分以上) / 複数人が同時に使う状況 /
道具ありターンの① は**未測定**。「4 項目を満たす往復が実在する」までが今日の結論で、
「成立が確定した」ではない。

### 12.8 ★ 割り込みで踏んだ 3 段 — 1 つ直すたびに下の層が出た

**印象では 1 つも分からなかった。全部、計測ログを読んで出た。**

```
★ 1  response.cancel               → 5 回中 4 回 `Cancellation failed: no active response found`
                                     ★★ モデルは**喋る速さより速く作る**。聞こえている最中には
                                        生成が終わっている = 止めるべき生成が無い
★ 2  conversation.item.truncate    → 送れた。★★ **505〜6658ms 鳴り続けた**
                                     これは**サーバの文脈しか直さない**
★★★★ 3  output_audio_buffer.clear     → ★ **113ms で止まった**。WebRTC 専用のクライアントイベント
```

★★ **押して話す (`turn_detection: null`) では、サーバの自動割り込みが働かない。**
公式の「WebRTC ではサーバが未再生の音声を自動で切り捨てる」は**発話検知が動いている場合**の話。
こちらから `output_audio_buffer.clear` を送らないと止まらない。**ここを読み違えていた。**

★ **手元の扱いも 2 つ効く**:
```
★ track.enabled = false で即座に黙らせる  (element の mute だと「止まったように見えて残りが後で鳴る」)
★★ 戻すのは「離した時」ではなく「★ 次の音声が始まった時」
   離した時に戻すと、古い応答の残りが鳴る = 「キューされる」の直接の原因だった
```

★ **調べ方の記録**: 3 段目は**ネットで探して**見つけた (利用者の提案)。
同じ症状の報告が上がっており、「**制御系 (シグナリング) と音声系 (データ) が切り離されていて、
truncate が成功しても配信は止まらない**」という説明が、こちらの実測 (505〜6658ms) と一致した。
★★ **自分の実装を疑う前に、同じ形で困った人がいないかを見た方が速い場面がある。**

### 12.9 ★ 計測の作り方で分かったこと

★ **AnalyserNode は「相手に聞こえているか」の計器にならない。** 手元の再生を止めても
ストリームは鳴って見える。★★ **基準③ には `output_audio_buffer.*` (サーバ発) を使う。**

★ **立ち上がり検知には保持時間が要る。** しきい値だけだと**言葉の切れ目を毎回「終わり」と拾う**
(実測で 8 往復に 301 回)。保持 400ms を入れて 1 往復あたり 37.6 回 → 3.25 回になった。
→ `client/src/utils/speechGate.ts`

★★ **「数字が全部おかしい」ではなく「どの数字がおかしいか」を分けること。**
上の 301 回のとき、基準① (離してから**最初の**立ち上がり) は**影響を受けていなかった**。
壊れていたのは「何秒話したか」と画面表示の方。**一緒くたに捨てると、正しい数字まで捨てる。**
