# 12. 配達役 (courier) — `@cc-` の便を、どの PC のコードエージェントにも中央から届ける

> **この文書の立場**: 設計 (2026-11-19 着手、利用者の「設計書から始めて」)。★ **2026-11-20 から、この機械の全 11 班を本番で配っている** (段階 1)。§13 が段階 2 (SSH)、§14 が段階 3 (相手の PC が HTTP で取りに来る)。
> 土台は PaneDeck 班の引き継ぎ文書 (`panedeck/docs/courier-design.md`、試作と試験の記録・踏んだ穴 12 個)。
> この文書はそれを本体の決まりに合わせて引き直し、PaneDeck 班が挙げた「未決」に答え、**作らないもの**を決める。
> ★ 2026-11-19 PaneDeck 班のレビューを反映 (§8 の 11〜16、§9 の「他の PC でエージェントを起こさない」、§10 の「様子を見る場所が変わる」、§7 の鼓動に載せるもの)。
> 関係: [#484](https://github.com/gamasenninn/tealus/issues/484) (受け取り側を PaneDeck に任せる) の続き。

## 1. なぜ作るか

`@cc-{班}` の便は今、各班のセッションが自分で待ち受けている (`listen-tealus` の Monitor)。

- Monitor は **30 分で黙って切れる**。張り直しはセッションの中の Claude が通知を見て行うので、
  セッションが止まる・`/clear` で手順を忘れると、**待ち受けが黙って止まる** (2026-09-20 に 7 時間、09-27 にも)
- 張り直しの間の便は、次の張り直しの「未処理の確かめ」でしか拾えない (2026-11-17 に 1 件、30 分遅れた。#484 のコメント)
- **誰がどこで待っていて、届いたか・詰まっているかが、本体から見えない** (「未処理 0 件」は正常の証拠にならない)

配達役は、この「待つ・届ける・様子を見る」を **1 か所に寄せる**。各セッションは待ち受けを持たず、
届いた便を Tealus MCP で読んで返すだけになる (#484 の考えと同じ。届け先を PaneDeck のペインに限らない形に広げたもの)。

> ★ **2026-11-24 16:41 から queue を書くのは本体** (`CC_INTAKE=server`、docs/14・#650)。この文書の「agent-server が書く・agent-server の持ち物・agent-server の `/pending`」は、
> **「受け付ける側のプロセス (今は本体)」と読み替える**。queue のファイル・1 行の形・URL (`/agent-api/cc-queue/...`) は変わっていないので、配達役は何も変えずに動いている。
> ★ 段階 3 で取りに来る `/pending` も本体が答える (`allowedRooms` は本体が自分の DB で引くので、§14 の「1 回ごとに agent-server が本体の `/api/rooms` を引く」は無くなった)

## 2. 何を作るか (一言で)

```
人が投稿 @cc-X …
   ▼
本体 ── queue (~/.tealus/cc-queue/X.jsonl)  ← 形は §4 で約束 (★ 11-24 まで書いていたのは agent-server)
   ▼
配達役 (★ 本体・agent-server とは別のプロセス。同じ repo の別の包み courier/)
   │  ブリッジの登録: 「班 X は、PC P の、届け先 A (会話 S)」
   │  ・届け先が空くまで待つ → 「新着 N 件 (最新 id=…)」を 1 通 → 動き出したかを確かめる → カーソルを進める
   │  ・届いた / 詰まっている / 落ちている を記録し、鼓動で本体へ知らせる (§7)
   ▼
届け先 (アダプタ): herdr (手元 / SSH 越し) ・ PaneDeck のペイン ・ codex queue
   ▼
エージェントが id を手掛かりに **本文を Tealus MCP で自分で読み、自分で返す**
```

★ 渡すのは **id だけ** (本文は渡さない。§8 の 1)。

## 3. 置き場所 (PaneDeck 班の未決 7)

- **同じ repo (tealus) の別の包み `courier/`**。rtc-server と同じ扱い (同じ repo・別のプロセス・別の `package.json`)
- **本体・agent-server とは別のプロセス**。配達役は他の PC へ入る鍵 (SSH) を持つ。メッセンジャーのサーバや AI の子プロセスが
  破られたときに、全部の PC へ入られないようにする。本体の「1 台・1 プロセス・同じ origin」は利用者の画面の話で、これとは両立する
- 動かす場所は **queue を書くプロセス (11-24 から本体、それまで agent-server) と同じ機械** (queue をファイルで読める。§4.3)。別の機械に置くときは HTTP の流れで読む
- 障害の窓口は本体班。PaneDeck 班は引き継ぎの文書とレビュー (2026-11-19 利用者判断)

## 4. queue の約束 (未決 1〜4)

### 4.1 1 行の形 — ★ この節で約束にする

```json
{ "id": "<メッセージの UUID>", "room_id": "<UUID>", "room_name": "…",
  "sender": { "id": "<UUID>", "display_name": "…", "role": "admin|user|guest" },
  "content": "…", "type": "text", "created_at": "<ISO>", "recipients": ["<project>", …] }
```

- `id` は Tealus のメッセージの UUID (`^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$`)。
  配達役は**この形だけを受ける** (PaneDeck の `^[A-Za-z0-9-]{1,40}$` と試作の `[A-Za-z0-9_-]{1,64}` のずれは、これで 1 つに決める)
- 配達役が使うのは `id` だけ。ほかの項目は読まない (本文を渡さないので要らない)
- ★ **本体側のテストで形を固定する** → `agent-server/__tests__/unit/ccQueueLineContract.test.mts` (段階 0、2026-11-19。新しい投稿と編集の 2 つの経路、鍵の集合と id の形。わざと鍵を足すと落ちることも確かめた)。
  形を変えるときは、この節を先に直し、AI班連絡で全班に知らせる (`@cc-` を付ける。受け手の記録を変えるため)

### 4.2 書き直される (未決 2)

追記だけではない。**2,000 行を超えると末尾の 80% だけ残して書き直す** (`CC_QUEUE_MAX_LINES`、一時ファイルに書いて rename)。
→ **行番号・文字数では追えない。id で追う** (listen-tealus と同じ)。読んだ最後の id が消えていたら、残りを全部「新着」とみなし、
件数は数えずに「新着あり (最新 id=…)」の 1 通にする (受け手は自分の watermark で読むので二重には扱わない)。

### 4.3 読み方 (未決 3)

| 読み方 | いつ | 続きから | 認証 |
|---|---|---|---|
| ファイル (`tail` 相当) | 配達役が agent-server と同じ機械 | 自分のカーソル (最後の id) | 要らない (ファイルの権限) |
| HTTP の流れ `/agent-api/cc-queue/stream?project=X&since=<id>` | 別の機械 | `since=<id>` (消えていたら残り全件 + warn) | ログインの鍵 (JWT)。受けられるのはその口座が入っている部屋の便だけ。**PC ごとに口座を分ければ PC ごとに分けられる** |

★ 最初はファイルだけで作る (§10 の段階 1)。

### 4.4 配る人は 1 人 (未決 4・8)

**1 つの queue (班) に配る人は 1 人。** ファイルと流れの両方、配達役と listen-tealus、配達役と PaneDeck のトリガーを
同じ班に向けると、同じ便が 2 回届く (処理済みの印 = watermark は受け手に 1 つしかない)。

- 配達役に移した班は **listen-tealus を止める** (Monitor を張らない。CLAUDE.md の「切れたら張り直す」もその班では外す)
- 配達役の中でも、同じ班を 2 つのプロセスが取り合わないよう **鍵 (lock) を取る**。鍵の持ち主のプロセスが生きているかを見る
  (強制終了で古い鍵が残った。PaneDeck 班 11-17)

## 5. ブリッジの登録 (未決 5)

- **置き場: 配達役の機械の `~/.tealus/courier/bridges.json` (repo の外)**。届け先の名前・PC・会話の id・SSH の鍵の場所を持つので、
  公開の repo にも本体の DB にも入れない
- 1 件 = 班 1 つ: `{ project, adapter: "herdr" | "herdr-ssh" | "panedeck-pane" | "codex", host?, agent, session_id?, enabled }`
- ★ **ボットと MCP の登録を自動でやる口は作らない** (§9)。相手の PC の用意 (Claude のログイン・MCP の登録・herdr の設置) は
  手順書で人が行う (courier-design.md の「相手の PC の用意」を土台にする)

## 6. 届け先 (アダプタ)

どの届け先も同じ 3 つに答える。**非同期で、失敗を返せること**。

```ts
interface Courier {
  status(): Promise<'idle' | 'busy' | 'blocked' | 'missing' | 'unknown'>;   // blocked = 人の判断待ち (打ってはいけない)
  deliver(text: string): Promise<{ ok: true; ref: string } | { ok: false; error: string }>;
  confirm(ref: string): Promise<boolean>;   // 渡したものが動き出したか
}
```

外のコマンドの呼び出しは注入する (`run(command, args) → { code, stdout, stderr }`)。「手元で実行」と「SSH で実行」はこの `run` の差し替え。
herdr・PaneDeck のペイン・codex の細かい約束は courier-design.md の「届け先の約束」をそのまま採る。

## 7. 様子を本体に出す (未決 6・9)

- **段階 1: 鼓動 (docs/09 §3.2) を使う。** 配達役は `POST /api/bot/heartbeat` に `{ name: "courier", info: { 班ごとの状態 } }` を送る。
  ★ info は本体の DB (`heartbeats`) に残るので、**班の名前と状態 (idle・blocked・missing と件数) だけ**にする。PC の名前・会話の id・届け先の名前は載せない (レビューの細かい点)
  見張り (docs/09) の `heartbeat` で「配達役が止まった」を業務メモに 1 回知らせる。**新しい口も画面も作らない**
- 班ごとの「詰まっている (blocked が N 分続く) / 落ちている (missing・unknown が続く)」は、配達役が自分で数え、
  続いたら業務メモに 1 回だけ知らせ、戻ったら ✅ (見張りの書き方に合わせる)。★ 確認待ち (blocked) には打たない (§8 の 4)
- 段階 2 (きっかけ待ち): 管理画面 (dashboard) に班ごとの一覧。業務メモの知らせで足りなくなったら
- ★ **2026-11-20 に作った (利用者「1、2 をまず作ってみないか」「A でつくって」)。**
  - 見張り: `server/config/watchdogs.json` に `courier` (鼓動 5 分)。止まった・`info.problem` を業務メモに 1 回
  - 本体の管理画面に「AIの班」のタブ (`GET /api/admin/courier`、システム管理者だけ)。班 / 状態 / 新着 / いつから。鼓動が 5 分古ければそう出す
  - 鼓動の班ごとに `since` (その状態になった時刻) を足した
  - ★ 新着が無くても **10 秒ごとに届け先の状態を見る** (状態が変わったら鼓動も 1 分を待たずに送る。画面は開いているあいだ 10 秒ごとに読み直す) (以前は新着があるときだけ見ていたので、便が無いあいだの確認待ちに気づけなかった。
    11-19 のフォルダ信頼の確認がそれ)。見るだけで打たない・カーソルは動かさない

## 8. 守ること (PaneDeck 班の「踏んだ穴」と安全から)

1. **本文ではなく id だけを渡す。** 本文を流すと、書いた人が user として指示できてしまう。文面はひな型だけから作る。
   id は §4.1 の形で検査し、外れた行は打たずに記録する (中身は写さない)。**壊れた行 1 つで止まらない**
2. **送っただけでは届いたと言わない。** 動き出したのを見てからカーソルを進める。押し直しは **Enter だけ** (3 回まで)
3. **まとめて 1 通。** 作業中に来た便は、空いてから「新着 N 件」1 通にする
4. **確認待ち (blocked) には打たない。** 打った文字が確認への答えになる
5. **カーソルは受け付けられた範囲までしか進めない。** ファイルに、一時ファイル → rename で書けてから進める
6. **二重配達の隙間** (受け付けからカーソルを書くまでに落ちる) は、受け手の watermark で同じ id を弾く
7. **届け先が落ちたら理由を出す。** 黙って溜め続けない。再試行は間をあける (15 秒〜)
8. **配達の上限。** 暴走したら保留し、捨てない。人が再開するまで戻さない
9. ~~SSH の鍵は届け先のコマンドだけに限る~~ → **保留** (2026-11-19 利用者、PaneDeck 班経由。届け先の PC は業務用で、配達役の機械が管理するもの。今は配達役の機械がほぼ何でもできるほうがよい。権限・制限は将来の運用の話として残す)。
   引用を cmd と PowerShell の両方で試験することは、保留にしない (文面が壊れるのを防ぐため)
10. SSH を使えない PC のために、**PC の側から本体の流れを受けに来る形** (PC 側の小さな配達役) も同じ登録で扱えるようにしておく
    (鍵を 1 か所に集めずに済む)。★ 段階 3
11. **打つことと Enter は別の出来事** (PaneDeck #28)。文面と CR を一度に送ると、Claude Code は貼り付けと見て CR を改行として入れ、
    実行されない (91 文字で 0/4)。herdr の `agent prompt` は内側で扱うが、PaneDeck のペインのアダプタや低い水準の口では必ず分ける
12. **herdr の `pane send-text` は使わない。** 確認待ち (blocked) への歯止めが無い。`agent prompt` だけを使う (4 の実装上の落とし穴)
13. **届け先の状態の出力は、行頭まで合わせて読み、試験にする。** 試作の起動スクリプトが `status: not running` を running と読んだ
14. **herdr の版を固定し、起動時に使う口があるかを確かめる** (保守者は実質 1 人)。更新の確認は切る
15. **確認待ち (blocked) の判定は、herdr の画面での判定に乗っている** (Claude の hook の連携は入れていない)。確かめたのは権限の確認画面での 1 回だけ。
    **Claude Code の版が上がったら測り直す** (段階 1 の終わりの印にも入れる)。Codex は未測定
16. **届く文面は、受け手の `handle-tealus` (Monitor を張らない手順) を指すひな型に固定する**。移すときに、その班のフォルダで handle-tealus が使えることを確かめる

## 9. 作らないもの

- **本体・agent-server のプロセスの中に配達役を置くこと** — 他の PC へ入る鍵を持つため (§3)
- **本文を届け先に渡すこと** — §8 の 1。読むのはエージェントが MCP で
- **1 つの班に 2 人の配る人** — 二重配達 (§4.4)
- **ボットと MCP の登録・相手の PC の用意の自動化** — 相手の PC に入って設定を書き換える力を配達役に持たせない。手順書で人が行う
- **届け先の画面の文字を広く読むこと** — 状態を見るのは届け先の決まった口 (herdr の `agent get` など) と、押し直しの判断の 1 行だけ
- **配達役が返事を書くこと** — 返事はエージェントが MCP で書く。配達役は「新着があります」以上を言わない
- **配達役が受け手の watermark を書くこと** — 読むだけ。処理済みの印は受け手の持ち物
- **配達役が queue を書く・切り詰めること** — queue は受け付ける側 (11-24 から本体) の持ち物 (§12.3)
- **画面から読んだ文字を、記録・鼓動・業務メモに写すこと** — 押し直しの判断に使う 1 行だけ見て、残さない
- **配達役が道具の確認 (blocked) に代わりに答えること** — blocked のペインには Enter も送らない
- **`bridges.json` を画面や API から書き換える口** — 登録は配達役の機械のファイルを人が書く
- **管理画面「AIの班」から班を足す・変える・消す** (2026-11-27 利用者判断) — 11-20 に案 A (画面は bot と部屋まで + 残りの手順を班の名前入りで案内) / B (A + 画面から止める向きだけ) / C (登録・削除まで、すすめない) を出したが、班は手順書と本体班の案内で問題なく足せているので当面作らない。**再開する条件**: 班を足す・入れ替える機会が増えて手順の抜けが出たとき → 案 A から
- **配達役が他の PC でエージェントを起こすこと** (2026-11-19 PaneDeck 班のレビューの 5) — 届け先が missing のとき、配達役は知らせるだけ。
  起こし直すのは相手の PC の自前の起動 (タスク スケジューラの S4U + `--resume`。試験でもこれで戻った) で、手順書に入れる。
  ★ 配達役と同じ機械の分は `courier/scripts/start.ps1` (2026-11-19、LP 班)。起こす表は配達役の `bridges.json` と**別のファイル**
  (`~/.tealus/herdr-agents.json`)。★ herdr はサーバを起こし直すと workspace は戻すが Claude は戻さない (試し用のセッションで確かめた)
  `bridges.json` の会話の id で配達役が `agent start -- --resume` する形 (案 b) は、配達役に「他の PC でエージェントを起動する力」を持たせるので採らない
- **herdr 以外の入れ物 (cmux・Orca など) への届け先** (2026-11-24 利用者「herdr に限定した方がエレガント」) — 配達役が要るのは
  「相手が空いている / 作業中 / 確認待ち (blocked)」を答える口と、動き出しを確かめて渡す口 (§8 の 4・12・13)。
  cmux (文字を送る `cmux send` はある。状態を聞く口は公式の説明に無い・Mac 専用) と Orca (`orca terminal send` と「手が空くまで待つ」はある。
  確認待ちを見分ける口は説明に無い・画面のアプリが要る) はどちらも確認待ちを見分けられず、打った文字が確認への答えになりうる。
  Claude Code の hooks で状態をファイルに書かせて補う案はあるが、入れ物ごとの差を配達役が抱えることになるので作らない。
  再開する条件: その入れ物が状態 (確認待ちを含む) を返す口を持ち、使いたい班が具体的に出たとき

## 10. 段階 (作る順)

| 段階 | 中身 | 終わりの印 |

| 3 | PC の側から受けに来る形・HTTP の流れで読む・管理画面の一覧 (きっかけ待ち) | — |

★ 移すのは 1 班ずつ。移した班は listen-tealus を止め、CLAUDE.md の「切れたら張り直す」の対象から外す。
★ **TUI でつないだ人が Ctrl+C を打つと、エージェントが止まって消える** (2026-11-19 PaneDeck 班で実際に起きた)。読むだけでつなぐ口は見つかっていない。様子を見る人に伝える

## 12. 監査で足したこと (2026-11-19、作る前の Fable の監査)

判定は「段階 0 は着手してよい。段階 1 のコードの前に、次を決めておく」。重大は 0。

### 12.1 受け手が本文をどう読むか (§2・§8 の 1 の補い)

- **段階 1 (この機械) の受け手は、手元の queue ファイルで読む** (今の `handle-tealus` の手順。watermark も `~/.tealus/cc-queue/.last_processed-X`)
- 別の PC には queue のファイルが無く、`/pending` は件数しか返さない。**段階 2 の前に「別の PC の受け手が id から本文を引く道」を決める**
  (候補: tealus MCP の `get_message_edit_history(message_id)` の current_content で 1 件の全文を取れる。ひな型に部屋の UUID も載せるか。試作がバックアップ PC でどう読んだかを PaneDeck 班に確かめる)
- `handle-tealus` は PaneDeck のペインが前提の文面 (届かないときはツールバーを見る、など)。**herdr の受け手向けに直すか、別の skill にするかを段階 1 で決める**

### 12.2 ファイルの読み方 (§4.2〜4.3 の補い)

- **開きっぱなしにしない。** 変化を見たら全部読んで閉じる (最大 2,000 行)。agent-server の切り詰めは一時ファイルを rename で入れ替えるので、
  Windows で開いたままだと rename が失敗しうる (失敗は warn だけで queue が伸び続ける。未測定 → 段階 1 の試験で測る)
- **読めない (EBUSY・EPERM・ENOENT)・空・末尾が改行で終わらない行は、新着ともカーソルの消失ともみなさず、次の回に読み直す。**
  これが無いと、読み損ねの一瞬で「残り全部が新着」の 1 通が出る。試験に「読んでいる最中の切り詰め」を足す
- **同じ id が 1 つの queue に 2 回入りうる** (編集で宛名を付け直した便、`handleMessageUpdated`)。カーソルは「最後に出てきた位置」で探す
- **初回 (カーソルが無い) は末尾から始める** (listen-tealus の `tail -n 0` と同じ。過去分は流さない。移す前の未処理は移す前に片づける)

### 12.3 配達役が書くファイル (§5 の補い)

- **`~/.tealus/courier/` に置く** (カーソル・鍵・出来事の記録・bridges.json)。**cc-queue のフォルダには書かない** (agent-server の持ち物で、`.tmp` もできる)
- project 名はファイル名になるので `^[a-z0-9](?:[a-z0-9-]*[a-z0-9])?$` で検査する

### 12.4 上限 (§8 の 8 の数字)

- **班ごとに 1 時間に 40 通を超えたら保留し、業務メモに 1 回知らせる。** (11-19 は 20 通。11-23 に利用者が 40 通へ上げた: 試験のやりとりで 1 時間に 21 通になり止まったため) 再開は人が `~/.tealus/courier/` の保留の印を消す (段階 1。口は作らない)。★ 印を消せば再起動は要らない: 配達役は印が消えたのを見た回にその班の数えを空にする。届かなかった回 (herdr の失敗) は数えない (2026-11-23 改善ループ 98。以前は数えがメモリに残り、印を消して 4 秒後にまた保留した)

### 12.5 許す道具を広げるときの歯止め (§11 の 4 の補い)

受け手は部屋のだれか (他班の AI を含む) が書いた本文を読み、無人で動く。**広げた道具が、そのまま注入されたときの被害の幅になる。**

- (c) 広げた一覧を移行の記録に残し、人が見直す
- (d) **移す班の auto_level を明記する。** L2 (人の OK 待ち) の班は、届いたあと人待ちで止まるのに、herdr からは idle に見えて blocked の知らせでは拾えない。
  → **段階 1 で移す班は L3 に限る**

### 12.6 段階 1 から詰まりを知らせる (§7 の補い)

- 段階 1 から、鼓動の `info.problem` に「班 X が確認待ち N 分」「届けたのに受け手の watermark が N 分進まない」を入れる。

## 13. 段階 2: SSH 越しの herdr (別の PC) — 2026-11-20 着手

### 13.1 形

### 13.3 相手の受け手が本文をどう読むか (12.1 の答え)

  相手の `handle-tealus` は http mode の catch-up をこれで行い、本文は今までどおり MCP で取る。watermark は相手の `.claude/.last_processed-X`
- ★ 切り替えのとき、相手の HTTP の待ち受け (Monitor か PaneDeck の service の `cc-stream.sh`) を止める (配る人は 1 人、§4.4)

### 13.4 相手の再起動からの戻り

## 14. 段階 3: 相手の PC が HTTP で取りに来て、相手の中の herdr に渡す — 2026-11-21 着手

★ 2026-11-21 利用者「HTTP 版を作ってから移す」(dbbackup班の移し方)。PaneDeck 班の案 (2026-11-20、10/10 に別の機械で HTTP で受けて画面に打つ 1 便を本番で通している)。
§13 (SSH) は消さずに残す (試験済みの代わりの道)。

### 14.1 形

- **相手の PC でも配達役を動かす**。中央の配達役はその班を持たない (配る人は 1 人、§4.4)。
  相手の配達役は便を **agent-server の `GET /agent-api/cc-queue/pending?project=X&events=1`** で取り、**手元の herdr** に打つ (段階 1 と同じアダプタ)
- 取った行は id だけを相手の手元の写し `~/.tealus/courier/queue-mirror/<班>.jsonl` に足す。配る輪 (tick) は写しのファイルを今までどおり読むので、
  カーソル・まとめて 1 通・上限・確認待ち・戻りが分からないときの扱いは**段階 1 と同じもの**を使う (配る判断を 2 つ書かない)
- `bridges.json` の 1 行: `{ "project", "adapter": "herdr", "agent", "queue": "http", "enabled", "dry_run" }`。取りに行く先とログインは `auth.json` (`api_url`・`login_id`・`password`)
- ★ ログインする口座は**その班の bot の口座**。理由: (1) `/pending` は呼んだ人が入っている部屋の便しか返さない = 班の口座ならその班が読める便とちょうど同じ
  (2) 鼓動は (口座, 名前) ごとに 1 行なので、中央の配達役の鼓動を上書きしない (管理画面「AIの班」には送った口座ごとに 1 段で出る)
  (3) 相手の PC には今の HTTP の受け取り (listen-tealus の http mode) のためにこの口座の資格情報が既にある。新しい口座も新しい鍵も増やさない
- SSH の鍵を中央に置かない・相手の herdr を管理者で起こさなくてよい (§13.5・docs/13 §5.5 の危うさが消える)。代わりに相手に Node 24 と `courier/` が要り、見張る相手が 1 つ増える

### 14.2 写しの決まり

- 写しの最後の id を `since` にして取る。★ `since` が queue に無い (切り詰め) と agent-server は**残り全部**を返すので、写しに**既にある id は足さない** (id で重複を消す)。
  これで「since の後ろだけ」と「全部」のどちらが返っても写しは正しい
- 写しが無い (初めて) は `since` なしで取り、全部を写す。配る輪は初回は末尾から始める (過去分は流さない) ので、写した過去分は配らない
- ★ 写しが**無い**のは「まだ取り寄せていない」こと。手元の queue のように「先頭から」の印を置くと、最初の取り寄せで入った過去分を全部配ってしまう。
  取れたら便が 0 件でも**空の写しを作り**、配る輪は空の写しを見て「先頭から」の印を置く (次の最初の便を飛ばさない)。写しは置き換えで書くので、書きかけで空に見える瞬間は無い (2026-11-21、移す前の見直しで足した)
- 写しに書くのは `{"id"}` だけ。本文・部屋の名前・送り主は書かない (§8 の 1。受け手は本文を MCP で取る)
- 写しは最後の 2,000 行に切り詰める (queue と同じ上限、§4)。書き換えは一時ファイル → rename
- 取れない (つながらない・401 のあと取り直しても 401・500) ときは写しを触らない。配る輪は前の写しで回る (新着が来ないだけ)。続けて失敗したら記録に残す
- 取りに行く間隔は 5 秒。1 回ごとに agent-server が本体の `/api/rooms` を 1 回引く (1 日 約 17,000 回、1 班あたり)
- ログインの鍵は使い回し、401 のときだけ 1 回取り直す (listen-tealus の #427・鼓動と同じ)

### 14.3 移すときの順 (dbbackup班)

1. 相手の PC に `courier/` と Node 24。`auth.json` は今の受け取りの資格情報 (`~/.tealus/cc-auth.json`) と同じ口座
2. 相手の herdr を**相手のログイン時に普通の権限で**起こし、dbbackup班の会話 (同じ会話の続き) を herdr の中で起こす。試験の hb1 を片付ける
   - ★ 実際は (2026-11-21) ログイン時のタスクでなく、相手の利用者の**スタートアップ**フォルダに `start.ps1` を呼ぶ `.cmd` を置いた。管理者の操作が要らず、普通の権限で起きる。
     配達役の置き場は `C:\app\tealus-courier` (repo の `courier/` の `src`・`package.json`・`scripts/start.ps1` の写し。依存は無い)
   - ★ 最初の 1 回も SSH 越しには起こさない (管理者の権限になる、§13)。相手の画面でサインインし直すか、スタートアップの `.cmd` を開いてもらう
3. 空回し (`dry_run: true`) で、今の HTTP の受け取りと記録 (ids) を見比べる
   - ★ 実際は飛ばした: 相手の PC が当日 12:35 に再起動していて、今の受け取りは既に止まっていた (見比べる相手が無い)。便は 11-16 が最後で、そこまで処理済み。代わりに相手の PC で取り寄せを 1 回だけ一時フォルダに試した (61 件・最後の id が処理済みの印と一致)
4. 本番に切り替える瞬間に、相手の今の HTTP の待ち受けを止める (配る人は 1 人)。handle-tealus は listen-tealus §2 の http の数え方 (`.claude/.last_processed-{班}` と `/pending`) で本文を取る
5. 本体の見張り (`server/config/watchdogs.json`) に、相手の配達役の鼓動 (送り主 = 班の口座、名前 `courier`) を 1 行足す
