# 実装ノート — 不変条件と落とし穴

設計書 (01〜03) が「何を作るか」なら、本書は「**触ると壊れる非自明な約束事**」の索引。
多くは該当ソースの docstring に一次情報があり、ここはその所在と「なぜ」を集約する
(bus-factor / 属人性対策)。新しく触る前に該当項を読むこと。

---

## 1. TypeScript / ESM ビルドレス実行 (#330)

- **サーバ系 (server / agent-server / rtc-server) は Node 24 の native type stripping で `.mts` を直接実行**。トランスパイル工程は無い (`node src/app.mts`)。`engines: >=24`、Docker も `node:24`、CI も 24 のみ。**Node 22 系では起動しない** (フラグ無しで型注釈を解釈できないため) ([[03_アーキテクチャ設計]] の #330 注記)。
- **ローカル import は必ず `.mts` 拡張子付き** (`import { x } from './foo.mts'`)。nodenext の要請。
- **`__dirname` は使えない → `import.meta.dirname`**。`import.meta.main` は Node 24 のみ。
- 型検査は実行と分離: 各プロジェクト `npm run typecheck` (`tsc --noEmit`)。CI が全プロジェクト + root CLI で走る。**テストは @swc/jest で型を検査しない**ので、型退行は typecheck でしか捕まらない。

## 2. ESM の import 巻き上げ由来の落とし穴 (テスト・起動で多発)

ESM は `import` を**モジュール本体の平文より前に評価**する。これが以下の温床:

### 2a. モジュール読込時に env / file を読む箇所
`const X = process.env.Y || 既定` を**モジュールトップで**評価している箇所は、import した瞬間に確定する。テストで後から env を差し替えても効かない。既知の箇所:
- `server/src/middleware/auth.mts` — `JWT_SECRET` (production 未設定なら **throw**、dev のみ警告付き fallback。§5)
- `server/src/services/transcriptionConfig.mts:23` — `CONFIG_PATH` (guideline file の場所)
- `agent-server/src/config.mts:14` — `TTS_PROVIDER` ほか
- agent-server の `middleware/auth.mts` / `routes/settings.mts` も同様

→ **テストでこれらの env/file を差し替えたい時は、`import` でなく env 代入後の `require()` (+ 必要なら `jest.resetModules()`) で遅延ロードする**。実例: `server/__tests__/unit/transcriptionConfig.test.mts` / `dictionaryLoader.test.mts`。

### 2b. SUT がモジュール読込時に mock client を生成 → TDZ
SUT がトップレベルで `new OpenAI()` / `spawn()` / `new pg.Pool()` 等を実行する場合、テストの外側 `const mock = jest.fn()` を `jest.mock` factory から参照すると **"Cannot access before initialization"**。
→ **factory 内で mock を生成し `(MockCtor as any).__mockX = fn` で公開、import 後に取り出す**。実例: `agent-server/__tests__/unit/router.test.mts` (openai) / `deep.test.mts` (child_process) / `sessionManager.test.mts` (pg)。

### 2c. @swc/jest × jest.config の地雷 (jest.config.js のコメント参照)
- `transform` を定義すると default の babel-jest が外れ、`.js` テストの `jest.mock` 巻き上げが消える → `'^.+\\.js$': 'babel-jest'` を明示復元 (server/agent-server 両 jest.config)。
- swc の CJS interop は `import * as X` をプロパティ複製するが **getter 記述子は保持**。テストから mock 値を動的書換えする場合は getter/setter で定義 (実例: router.test の config mock)。TS 上 namespace import は readonly なので書換え側は mutable 型へ cast。
- `node:` prefix は src と mock target で一致させる。

## 3. テストを machine 非依存に保つ約束

- **本番 config file (gitignore・端末固有) の内容にテストを結合させない**。env override + tmp fixture で自給する ([[feedback_test_db_guard]] / test_file_guard パターン)。過去 `dictionaryLoader.test` が `config/transcription_guideline.json` の実内容 (ローカルのみ) に依存し CI で落ちた。
- 本番DB破壊防止: `request(app)` 等は本番 DB に繋がりうる。テストは専用テスト DB (port 5433) のみ。

## 4. ランタイム構造の不変条件

- **`server/src/io-registry.mts`** — routes↔app は真の循環 (app が全 routes を組む)。依存ゼロの registry で切断。app が起動時 `setIo()`、routes は `getIo()`。**routes から `app.mts` を直接 import しない**。
- **context-object パターン** (`server/src/services/lineMessageBridge.mts:24-` Option D) — メッセージ投稿の4経路 (socket / bot / voice / LINE) は sender を `{ id, display_name, avatar_url }` の context object で 1:1 に渡す。helper 内で DB query しない = test isolation とモジュール状態ゼロを保証。
- **★ `message.created` webhook を発火するのは 18 本の INSERT のうち 4 本だけ** (2026-08-23 実測に訂正。以前ここには「socket `message:send` のみ」と書いてあったが**誤り**だった): socket `message:send` / `routes/media.mts` の**転送** / `routes/voice.mts` / `services/postAsUser.mts` (= Bot API の `/push` とルームトリガー #382)。**通常のメディアアップロード・`/push-image`・`/push-file`・LINE 経由・system メッセージには付いていない。** 全 18 本の一覧と「意図か不明か」は **[`docs/07_投稿経路と付随処理.md`](07_投稿経路と付随処理.md)** (#383)。REST `POST /rooms/:id/messages` (`server/src/routes/messages.mts`) は INSERT するだけで **webhook も socket 配信もしない** (updated/deleted/reaction は発火する)。→ webhook 経由の下流 (agent-server の Light/Deep dispatch、`@cc-*` の cc-queue routing) を効かせたいメッセージは **socket 経路で送る**こと。client から新規メッセージを送るときは REST 直呼び (`api.request` / `sendStamp` 型) でなく socket 優先 (`MessageInput.handleSend` パターン) にする。#336 で FormBubble の回答が REST 送信ゆえ `@cc-organon` が cc-queue に届かず organon が起動しなかった実例あり。ユニットテスト緑でも統合で silent に効かない種類。
- **codex は 1 turn で `agent_message` を multi-emit** (`agent-server/src/agents/deepCodex.mts:267-`) — user 向け応答は **「最後の非空」を採用** (accumulate ではない)。lightV2.mts で確立済。
- **★ organon の「型」は分類ではなく配送条件** (`server/scripts/organonDictProjection.mts`、#331) — 射影は **`Role` / `Organization` かつ `status=confirmed` のみ**を辞書テーブルへ通す。`Polyseme` / `Location` / `Shared-kernel` / `Protocol` は **どこにも配送されない** (2 型 + 残り全部、という非対称)。
  <br>★ organon 側にとって型は「意味の分類」だが、本体にとっては「配送するか」の判定。**同じ札が両者で別の役割**を持つ。2026-08-18 に [[飛行船]] (自社) が `Shared-kernel` で起票され、STT の garble 4 語 (コセン/ゴーセン/資根線/資源線) が**辞書に 1 語も届いていなかった**。カードも別名も正しく、**棚だけが違った**。organon 側は hazard 節に「型の選択は確認済でない」と留保まで書いていたが、**留保が何を壊すかは本体班が伝えていなかった**。
  <br>★★ **射影は entry 単位でしか通せない** — 同じ entry に「辞書に載せたい別名」と「載せたくない別名」が混在しても分けられない (実例: `道場側-ビレッジ側` の `整備A` は無線の呼び出し名として実発話される)。alias 単位の出し分けは**未実装、実害が出るまで作らない**。
  <br>★★★ **射影ルール (述語・型・status) は organon との公開契約**。organon 側は `CLAUDE.md` の境界節に同じ表を持ち、**変更時は AI 班連絡へ事前に一報**する運用。**こちらが変えるときも同じ**。片側で黙って変えると、相手は「登録したのに効かない」を自分の側で探し続ける。
  <br>★ 反映は自動: `organonWatcher.mts` が `ORGANON_TTL_PATH` を 5 分間隔で hash 監視 → `syncFromOrganon` → `refreshVocabFromTable` → `config/dictionary.local.ttl` 再生成。届いたかの確認は **local.ttl の該当 subject ブロックを見る** (`grep -c` の件数で判定すると別 entry の別名を拾う。実際にやった)。
- **単一サーバ・同一オリジン** ([[00_what-is-tealus]] / 単一サーバ simplicity) — front/back を generic に分離しない。5173 等の dev/prod 漏れは front/back 結合の兆候ではなく設定漏れ。
- **★ PWA 更新検知は Service Worker に依存しない経路で行う** (#356) — Workbox 生成の SW は `NavigationRoute` + `createHandlerBoundToURL("index.html")` で、**`request.mode === 'navigate'` で判定するため URL に依存しない**。ゆえに (a) サーバの `Cache-Control` は SW の手前で止まる (b) キャッシュバスター付き URL でも素通りできない。precache に `ExpirationPlugin` は無く**有効期限も無い**。iOS の standalone PWA は SW スクリプトの更新チェックが走らず、**2 日放置しても自己回復しないことを実測で確認済** (2026-07-30)。
  - 検知は `client/src/hooks/useVersionCheck.ts` が、ビルド時に焼き込んだ `__BUILD_ID__` (`client/src/utils/buildVersion.ts`) と `GET /api/version` (`server/src/routes/version.mts`) を照合して行う。`/api/*` は precache 対象外かつ `navigateFallbackDenylist` (`client/vite.config.js`) にも入るため、**SW が古い画面を返していてもこの fetch だけはネットワークに届く**。ここが生命線。
  - **`version.json` を precache に入れてはいけない** — `vite.config.js` の `workbox.globIgnores: ['**/version.json']` を外すと古い ID が返り続け、**更新検知そのものが silent に死ぬ**。
  - `/api/version` は**リクエストごとに `dist/version.json` を読み直す**。起動時に固定すると稼働中の再ビルドで「いつまでも更新あり」になる。
  - 検知の契機は `visibilitychange` が本命 (iOS の PWA は復帰してもナビゲーションが起きない)。Android Chrome は SW 更新経路が正常なのでバナーが出る隙がなく、**バナーの実機検証は「開いたまま裏に回す → 再ビルド → 戻る」**で行う (Android / iOS 両方で確認済)。
  - 静的配信の `Cache-Control` は `server/src/utils/staticCache.mts` が性質で振り分ける (#355。入口 = `no-store` / ハッシュ付き `assets` = `immutable`)。入口判定を `assets` 判定より**先**に置く順序に意味がある。

- **★ cc-queue の起床通知は file と HTTP の 2 出口があるが、消費側は片方だけを有効にする** (#214) — `agent-server/src/webhook/ccQueue.mts` の `appendCcEvent` は jsonl への append の**後ろで** `publish()` (HTTP 購読者へ配信) と `trimIfNeeded()` を呼ぶ。append 自体は #213 から不変。消費側 (`.claude/cc-tealus.json`) で `queue_path` と `stream_url` を**両方**設定すると、同じ mention を 2 回受け取り二重に返信する。
  - **cc-queue dir は単一の agent-server プロセスが所有する** — トリム (`CC_QUEUE_MAX_LINES`、既定 2000 → 1600 行) が read → rewrite なので、同じ dir を複数プロセスが書くと切り詰めで行が消える。
  - **HTTP 配信は購読者ごとの `allowedRooms` で必ず絞る** (`ccSubscribers.mts`) — beacon を書くのは agent-server の bot、消費して返信するのは CC セッションの bot で**別 principal**。参加ルームが違うため、絞らないと「返信できない (bot API が 403) イベントで起こされる」うえ、読み手の権限を超えた本文が流れる。`allowedRooms` は接続時に**呼び出し元のトークンで**本体の `/api/rooms` を引いて確定する (agent-server の `authenticate` は署名検証のみで DB を見ないため、この転送が無効化ユーザーの穴も塞いでいる)。
  - **★ 同報 (`@cc-a @cc-b`) は「1 行目の先頭に並んだもの」だけ。メッセージ全体を走査してはいけない** (#387) — `CC_MENTION_RE` は `/m` なので **どの行の行頭にも当たる**。全体を `matchAll` にすると、AI 同士の引用や「各班の宛先はこれ」という案内表の行頭 `@cc-*` まで配送先になり、**1 通で 7 セッションが起きる**。cc-queue 全 1323 便での実測は「1 行目の先頭に並べた便 2 件 = 全部本物 / 1 行目以外に行頭 mention がある便 2 件 = 全部誤配」で**完全に排他**だった。同報は `addressRunCcNames()` (最初の非空行の**宛名欄**のみ、`/m` なし) で取り、それ以外は従来どおり 1 宛先に落ちる。<br>★ **2026-09-03 (#393) に「行頭に並んだもの」を「宛名欄に並んだもの」へ広げた** —— 宛名欄 = 最初の非空行の行頭から連続する mention の並びで、`@アシスタント @cc-phronesis` のように `@cc-` の前に別の mention が付いていてもよい (**mention でない語が来たらそこで終わり**)。**連名の扱いは不変**。緩める幅は測って決めた: 全期間 1747 便で「どこでもよい」= 新規 201 便 (うち 134 便が Claude 自身の引用 = 自己ループ防御が消える) / 「第 1 非空行のどこでも」= 新規 9 便 (8 便が誤報) / 「宛名欄」= 新規 1 便・誤報 0。実装を実データに当てて **1509 → 1510 便、落ちた便 0** を確認済み。<br>★ **`.match()` → `.matchAll()` では同報にならない** —— `^` にアンカーされているので `@cc-a @cc-b` の 2 つ目は元々 match しない。<br>★ **受付エコー (`emitCcAck`) は宛先ごとに呼ばない** —— room の status は 1 つしか無く、N 回押し込むと上書きし合って最後の 1 件しか見えない。`projects` を渡して 1 回で出す。<br>★ **編集経路 (`message.updated`) は差分で配る** —— 「付いたか / 付いていないか」の真偽値で見ると、宛先を 1 つ足した編集で既に届いている班をもう一度起こす。<br>★ **返信で宛先を並べ返すと N 体ループになる** (自己ループ防止は「宛名欄にあるか」だけ、`docs/06` §6.1)。慣習で止めている: 同報は最初の便だけ / 返信の先頭 mention は発信者 1 つ (`listen-tealus` SKILL.md §5)。**送信者で制限する手は使えない** —— 実データの同報 2 件のうち 1 件は発信者が Claude だった。
  - **消費側の `since` は watermark ではない** — `.last_processed-*` (watermark) は reply 成功時にしか進まないので `since` に使うと未処理が再接続のたびに再送される。skill は受信済みイベントを別途ローカル log に落とし、その最終 id を `since` に使う。
  - **★ 認可は接続時のスナップショット。だから接続に寿命を持たせている** (#360) — `allowedRooms` は接続時に `/api/rooms` を引いた結果を保持し続け、JWT の検証も入口で 1 回だけ。**ルームから外された / ユーザーが無効化された / トークンが失効した、のどれも開いている接続を止めない**。`CC_STREAM_MAX_AGE_MS` (既定 55 分) で自ら閉じ、クライアントの再接続ループに再ログイン + 再認可をさせることで解消している。**この timeout を伸ばす / 外すと権限の更新が止まる**。既定を 55 分にしているのは nginx の `proxy_read_timeout` より短く取り、タイムアウト境界での不定な切れ方より自分の切断を先に来させるため。実測で 2 時間 26 分無切断の接続が出て顕在化した (無切断を達成したことで初めて見えた穴)。
    - **★ 訂正 (2026-08-22 に NAS 上で `nginx -T` を実測)**: ここに `proxy_read_timeout 3600s` と書いていたが**誤り**。`app.tealus.dev` の server ブロックは **60s** (`proxy_connect_timeout` / `proxy_read_timeout` / `proxy_send_timeout` とも 60、Synology のリバースプロキシが生成する形)。3600s は別ブロックの値だった。
      **つまり 55 分という値は誤った前提の上に選ばれている**。実際に接続を保っているのは max_age ではなく **15 秒ごとの heartbeat** (60s の無通信で切られる側に対して 4 倍の余裕)。max_age を延ばすかどうかを検討するときは、この 60s と heartbeat 間隔の関係で考えること。
      なお 8/21-8/22 の nginx `error.log` に `upstream timed out (110)` は **0 件**で、この 60s は発火していなかった (想定外切断の原因ではない)。
    - **★ 追記 (2026-08-23、初めて発火した)**: agent-server を再起動したところ、3 本とも **59.783 / 59.784 / 59.842 秒** 保持されてから切れた (幅 0.059 秒 = 60s タイマの実物)。機構は上と整合する —— **60s を抑えていたのは 15 秒ごとの heartbeat で、その発生源である agent-server が死ぬと抑えが外れる**。その間クライアントは死んだ上流に繋がったままで受信できない。
      <br>同じ日の **server 再起動は 1 秒で撤去され空白 19 秒**、**agent-server 再起動は空白 67.8 秒**。同じ「予告つき再起動」で 3.5 倍の差が付いていた。→ `proxyRes` が閉じたら `res` も閉じる (`endDownstream`) を入れて解消 (**発効 2026-08-23 13:46:27**)。**この 60s は「想定外切断の原因ではない」が「計画停止のコストの正体」だった。**
- **★ 計器の原則: 測れないものを項目に置かない** (2026-08-23、Mac セッションの言い方を採用)。
  > **「沈黙が 2 通りに読める」より、「読めない値が 1 通りに読めてしまう」方が悪い。**

  沈黙は少なくとも「分からない」と読まれるが、壊れた値は**確信を持って誤読される**。同日 3 例:
  `client=+0.000s` (リクエストを読み終えた時刻を「下流が切れた時刻」として出していた) /
  `side=client` (proxy 自身が落ちた場合も client と出る。**規則を直したのに、同じ穴が規則の中に残っていた**) /
  `実損` の project キー衝突 (同時に落ちた 2 本が 1 本に潰れ、28 秒が 10 秒と出た)。
  → **判定できないときは `unknown` と書く。項目ごと消すのも可。埋めてはいけない。**
  - **★ ストリームの仕分けは除外方式でなく許可方式にする** — SKILL の接続コマンドは当初 `grep -v '"__hb"'` で heartbeat だけを落としていたが、**proxy の 504 などで返る HTML / テキストのエラー本文が素通りして受信ログに混ざり、`SINCE` の計算 (`tail -1` → JSON.parse) が壊れて空になる**。結果、**再接続で切断中の mention を丸ごと取りこぼす** (切断を拾うための仕組みが、切断のたびに壊れる)。2026-08-01 の dogfood で実際に踏んだ。`{"id"` で始まる行だけをログに入れ、それ以外は通知のみにする。**#360 で切断が定期的になったため、この欠陥を踏む頻度が上がっている**。
  - Monitor は `persistent: true` のとき `timeout_ms` を無視し、**コマンドが exit すると監視ごと終わる**。curl の単発では切断時に黙って聞かなくなるので、skill 側は `while true` の自己再接続ループにしてある。`tail -F` には無い HTTP 固有の失敗モード。
  - **★ 切断の理由はサーバが伝える。経過時間から逆算させない** (#366) — 寿命で閉じるときは `{"__bye":{"reason":"max_age"}}` を `res.end()` の**前に**書く。消費側が「経過秒が寿命に近いか」で判定する方式は、**`date +%s` が単調増加するという前提**に乗っていて成り立たない (壁時計なので NTP が動かす)。実際 2026-08-02 に別マシンで `SEC=3298` と記録され、サーバ側の実測 3300 秒ちょうどの寿命切断が「想定外」として通知された (2 台の時計が 55 分で 2 秒ずれていた = 606 ppm で、自然なドリフトでは説明がつかない)。窓による判定は**予告を出さない古いサーバ向けの退避**として残っているだけ。

- **★ 片側しか持っていない情報は、持っている側から配る** (2026-08-02、cc-bridge で 1 日に 3 回同じ変換をした後に言語化) —— 運用ルールは、**情報を持たない側に「覚えておけ」と要求するので必ず腐る**。守られなくなった時点で、本当に必要な場面でも使われない。

- **★★ テストの替え玉が本番より親切だと、ずれは「合格の方向」にだけ出る** (2026-08-16、#371) —— 実物より**多く答える** stub は、**本番では成立しない条件でテストだけを通す**。
  <br>★ 実例: `learnFromEdit` の読み供給 stub を `async () => new Map([['とうしば','とうしば'], ['東芝','とうしば']])` と書いた。**本番の `getReadings` は `texts` に無い語を返さない**のに、この stub は**要求されていない term の読みまで**返す。→ 「reading が空の term でも通る」テストが **修正前から合格**していた (実装は何も変わっていないのに)。**stub を「要求された語にだけ答える」形に直したら、正しく落ちた。**
  <br>★★★ **落ちる方向のずれは気づけるが、通る方向のずれは気づけない。** → **DI する替え玉は「実物が答えないことは答えない」まで真似ること**。特に **Map/Record を丸ごと返す stub** は、引数を無視しやすいので危ない。
  <br>★ 同型: 同日 `AI班連絡` で、**未読の便を残したまま判断を送っている** (相手の反論が部屋に置かれた状態で「決まりました」と報告した)。**確かめる手間より先に結論を出す**という点で根は同じ。

- **★ `ttfb` は接続確立の指標にならない (cc-stream)** (2026-08-15) —— body の 1 バイト目は **最初の heartbeat** なので、`ttfb ≒ 15s` に張り付く (`heartbeatMs()` 既定 15000)。**108 秒しか生きなかった接続でも `ttfb=15.096`** で、**接続の寿命と無関係**。
  <br>★ **さらに `backlog` が先に書かれる** (`ccQueue.mts`: backlog の `res.write` → その後 `setInterval`)。**backlog が 1 件でもあれば 1 バイト目はイベント**になり、`ttfb` は**確立時間 (0.03s) に潰れる**。→ ★★ **`ttfb − 15.0` を指標にするなら、`接続:` 行の `backlog=0` と突き合わせた接続だけで見ること** (2026-08-10〜15 の 367 接続はすべて `backlog=0` だが、**「起きない」ではなく「まだ起きていない」**)。
  <br>★ heartbeat の **`setInterval` はリクエストハンドラ内** = **接続ごと・購読した瞬間から**。共通タイマへの相乗りではないので、購読ごとに位相が独立する。<br>★ **`heartbeat_ms` / `max_age_ms` は購読応答で既にクライアントへ渡している** (#361)。**ただし渡しているのは「間隔」だけで「起点」ではない** —— 起点は契約に出ていないので、クライアント側が推定するしかない。

## 5. セキュリティの約束

- **JWT_SECRET は本番で必須** — `server/src/middleware/auth.mts:10-11` と `agent-server/src/middleware/auth.mts:13-14` が `NODE_ENV=production` かつ未設定なら**起動時 throw**。dev のみ警告付き fallback。この guard を弱めない (自己ホスト者が秘密鍵未設定のまま黙って起動する事故を防ぐ)。
- server と agent-server は**同じ JWT_SECRET を共有**し同じトークンで認証 (agent-server は DB ルックアップしない疎結合)。
- **★ agent-server は「送信元アドレス」で認可してはいけない** (#368) —— 本体サーバの `/agent-api` proxy (`server/src/app.mts:81`) は外部からのリクエストを `http://localhost:4000` へ中継する。したがって **agent-server から見ると、外部リクエストも loopback から届く**。「localhost からのみ許可」という内部 API を作ると `https://<host>/agent-api/<その path>` でそのまま破れる。内部用の口も**共有 JWT で守る**こと。<br>★ 逆に言うと、agent-server に生えた口は**すべて `/agent-api/` 経由で公開されている**とみなして設計する。`app.use('/cc-queue', authenticate, ...)` のように mount 側で認証を掛ける形が既定。

## 6. リポジトリ / 依存の衛生

- **`media/` はリポジトリに入れない** (実行時アップロード。tealus-media へ分離済・`.gitignore` 済)。`git add -A` は削除の巻き込み事故を招くので**パス指定で精密ステージ**する ([[feedback_media_dir_migration]])。
- **OSS ライセンス**: MIT。GPL/AGPL 依存の混入は各プロジェクト `npm run license-fail-on-gpl` (CI で全 ship プロジェクト実行) が弾く。
- **rtc-server → agent-server の横断 import** (`rtc-server/tts-speak.mts` → `agent-server/src/lib/tts-core.mts`、TTS ロジック共有) が1つある。rtc の型検査 CI は agent-server の deps も install している。新たな横断依存は増やさない方針。
